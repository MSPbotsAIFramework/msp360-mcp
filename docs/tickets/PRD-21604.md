# PRD-21604 · [Rewst Gap · New MCP] MSP360 Managed Backup · msp360_provider_login

Ticket: https://app.clickup.com/t/1dfhfaq80ek
Repo: https://github.com/MSPbotsAIFramework/msp360-mcp@main (c4c9439)
Work branch: dev/PRD-21604
Status: in progress

## Requirement understanding

One line: Add an MSP360 Managed Backup connector/MCP with a msp360_provider_login tool that logs in with the MSP360 provider account (UserName/Password) and returns an access_token for subsequent MSP360 Managed Backup API calls (gap found in the EMD Networking Services Rewst "MSP360" flow, 29 runs/365d, evidence grade A; mspbots-gap-register.xlsx item 38).

The ticket is one of six sibling "tool" tickets (PRD-21604–21609) that migrate specific steps of an
existing Rewst automation for client EMD Networking Services into Agent-platform MCP tools. In the
original Rewst flow, `custom.generic_request` first calls `POST /api/Provider/Login` with
`UserName`/`Password` to obtain a bearer `access_token`, then uses that token on later raw HTTP steps
in the same flow (`Authorization: Bearer <access_token>`). The reporter wants the Agent platform to be
able to do the same login step MSP360 requires before any other MSP360 call can succeed. Sources below
explain why this design does not reproduce that literal token hand-off (Agent never receives the raw
token) while still giving an Agent-callable way to confirm the MSP360 connection logs in successfully.

## Product design

### Goals / Non-goals

**Goals** (this ticket only):
- An Agent (or a user right after entering MSP360 credentials in the connect dialog) can ask "does
  this MSP360 connection actually work?" and get a clear yes/no answer, without any other MSP360 tool
  needing to exist yet — this is deliberately the smallest possible first tool in a brand-new,
  otherwise-empty connector.
- The check uses the exact vendor call the gap register names (`POST /api/Provider/Login`) and the
  exact field names the ticket calls out (`UserName`/`Password` in), so the Rewst-to-MSPbots mapping
  for this gap-register line item stays traceable.
- The connector follows the same connect-once / Header-credential pattern as every other MSPbots
  connector and as sibling ticket PRD-21273 already designed for this same repo (wiki:
  `ProductDocs/15-Capabilities.md` § "Connection forms") — no custom UI, and the two header names are
  identical to PRD-21273's.

**Non-goals** (explicitly out of scope for this ticket):
- **Returning the vendor's raw `access_token` to the Agent.** The ticket text describes this
  literally (mirroring the original Rewst flow, where the workflow engine itself held the token
  between HTTP steps), but handing a live bearer credential to the Agent would (a) contradict the
  three platform-wide contracts this whole repo already commits to — Header-only credentials,
  statelessness, per-request isolation (`~/.claude/skills/vendor-mcp-development/SKILL.md` "Runtime
  model" section) —
  and (b) contradict the product's own stated promise that "the AI never sees passwords or tokens."
  Rewst needed the token because its generic HTTP-step engine has no built-in per-vendor auth
  handling; this MCP server does the equivalent internally on every call, the same way PRD-21273's
  six tools already do. See Open questions (OQ2) and Tech design · Option analysis for the full
  reasoning.
- Listing companies, users, user-computers, packages, or domains — PRD-21605/21606/21607/21608/21609
  own those, respectively.
- Backup-health monitoring or plan start/stop — PRD-21273 owns those; zero overlap (confirmed in its
  own design, see Current state).
- Any token caching or reuse across calls. This tool makes its own fresh login call every time it is
  invoked (see Non-functional) — it is a connectivity check, not a session manager. If a later
  sibling ticket needs a shared token cache to avoid a vendor login call on every one of its own API
  calls, that cache is its own concern (and, per PRD-21273's own note, should consolidate into one
  `api_client.py` rather than duplicate).

### Acceptance criteria

- **AC1**: Given valid MSP360 provider credentials are supplied in the connector's headers, When the
  Agent calls `msp360_provider_login`, Then it receives `{"authenticated": true, "expires_in": <seconds
  or null>}` and the response contains no `access_token` field or any other raw credential material.
- **AC2**: Given the MSP360 provider credentials are rejected by the vendor (wrong password, revoked
  API credential), When the Agent calls `msp360_provider_login`, Then it receives a structured error
  envelope with `code: "unauthorized"` and `retryable: false` — never a raw exception, stack trace, or
  HTTP 500.
- **AC3**: Given the request to the MCP server is missing one or both required credential headers,
  When the Agent calls `msp360_provider_login`, Then the server returns HTTP 401 with a body listing
  which header(s) are required, and does not attempt a call to MSP360 at all.
- **AC4 (multi-tenant)**: Given two different MSPbots tenants call `msp360_provider_login`
  concurrently with two different sets of credentials (one valid, one invalid, in either order), When
  both requests are in flight at the same time, Then each tenant's response reflects only that
  tenant's own credentials — no tenant's success/failure result, cached token, or error is ever
  attributable to another tenant's request.
- **AC5 (security)**: Given any outcome of `msp360_provider_login` (success, rejected credentials, or
  an upstream error), When the tool returns its result or the server writes a log line for the call,
  Then neither the submitted password nor the vendor's `access_token` ever appears in the tool's
  response body or in any log output.
- **AC6 (resilience)**: Given MSP360's login endpoint is unreachable, times out, or returns a 5xx
  response, When the Agent calls `msp360_provider_login`, Then it receives a structured error with
  `code: "upstream_error"` and `retryable: true`, not an unhandled exception.

### Open questions

- **[non-blocking, assumption] OQ1**: MSP360's primary-source documentation
  (`help.mspbackups.com/mbs-api-specification/get-started-api`, fetched 2026-11-03) confirms the
  response carries `access_token` but does not explicitly document an `expires_in` field or its
  units; it only says the token is "temporary." The ticket description asserts `expires_in` is part
  of the response. **Assumption**: treat `expires_in` as an optional integer-seconds field — read it
  if present, return `null` in the tool's `expires_in` field if absent (AC1 covers both). If this
  assumption fails (field has a different name or shape), only `api_client.py`'s response parsing
  changes; the tool's own contract is unaffected. Dev should confirm against a live MSP360 response
  if a test account becomes available and record what was actually seen in Self-test.
- **[non-blocking, this ticket's resolution of PRD-21273's OQ3] OQ2**: The ticket's literal ask is a
  tool that returns the vendor's raw `access_token` for the Agent to carry on later calls, mirroring
  Rewst's own orchestration. This design does not build that — see Non-goals and Tech design · Option
  analysis for why, and the "Decisions made by DEV01" note on this ticket's comment thread. **This is
  a judgment call made in the absence of a product-side answer, not a product decision requiring
  sign-off**: it follows the same Header-only/stateless contract every other MSPbots connector
  (including this repo's own sibling ticket PRD-21273) already follows, and the platform's own
  published promise that "the AI never sees passwords or tokens." If product specifically wants the
  Agent to be able to obtain and hold a raw MSP360 bearer token (e.g., for some out-of-band use the
  platform doesn't support today), that is a cross-cutting platform change, not something one
  connector should do on its own — flag it in a comment and this ticket's tool can be revisited.

## Tech design

### Conclusion

Build the MCP service skeleton (Python 3.12 + uv + FastMCP, per the vendor-mcp-development SOP's
reference layout) in the still-empty `msp360-mcp` repo — or reuse it if a sibling ticket's dev work
has already landed it by the time this ticket's dev leg starts — and add one new tool,
`msp360_provider_login`, plus the `api_client.py` helper that performs the vendor's login call. The
tool takes no parameters (credentials come from the two headers this repo already uses), calls
`POST https://api.mspbackups.com/api/Provider/Login`, and maps the result to a small, token-free JSON
object or a structured error. No token cache, no session state — the simplest design that is still
useful on its own before any other MSP360 tool exists in this repo.

Nothing — `path:line` for "the whole repo" is `README.md:1-2`, a two-line placeholder

### Data & API contract

**Header credentials** (identical to PRD-21273's design — same repo, same connector, must not
diverge):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Msp360-Username` | Yes | MSP360 Managed Backup provider-account username | MSP360 admin portal → Settings → API credentials |
| `X-Msp360-Password` | Yes | MSP360 Managed Backup provider-account password | Same as above |

**Vendor call** (inside `api_client.py`):

```
POST https://api.mspbackups.com/api/Provider/Login
  body: {"UserName": "<from X-Msp360-Username>", "Password": "<from X-Msp360-Password>"}
  200 -> {"access_token": "...", "expires_in": <seconds, optional — see OQ1>}
  401/403 -> credentials rejected
  5xx / timeout -> upstream error
```

**Tool contract** (Agent-facing, returned as a compact JSON string per SOP §4.1):

```
msp360_provider_login() -> {"authenticated": true, "expires_in": <int seconds, or null if the
                             vendor response did not include it>}
```

No parameters. No `access_token` field, ever, in a successful response — this is the entire point of
the design (AC1, AC5).

**Error envelope** (SOP §4.2):

| Vendor / server condition | `code` | `retryable` |
|---|---|---|
| Missing `X-Msp360-Username` and/or `X-Msp360-Password` header | *(HTTP 401 from middleware, before any tool-level envelope — AC3)* | n/a |
| `POST /api/Provider/Login` returns 401 or 403 | `unauthorized` | false |
| Vendor returns 400/422 (malformed request body — should not happen with well-formed headers, kept as a defensive mapping) | `invalid_argument` | false |
| Vendor returns 429 | `rate_limited` | true |
| Vendor returns 5xx, or connect/read timeout | `upstream_error` | true |
| Anything else unexpected | `upstream_error` | true |

**Backward compatibility**: N/A — brand-new tool in a brand-new (or still nearly-empty) repo. Tool
name uses the `msp360_` prefix so it cannot collide with any other vendor's tools in the same Agent
session, or with this repo's other five planned tools (`msp360_list_companies` etc., owned by
sibling tickets).

### Key flow / sequence

```
Agent -> Gateway -> msp360-mcp: msp360_provider_login()
  msp360-mcp: read X-Msp360-Username / X-Msp360-Password from the request (middleware);
              missing either -> 401, do not call the vendor (AC3)
  msp360-mcp -> MSP360 API: POST /api/Provider/Login {UserName, Password}
  MSP360 API -> msp360-mcp: 200 {access_token, expires_in?}  |  401/403  |  5xx/timeout
  msp360-mcp: discard access_token immediately after reading expires_in (if present);
              never place it in the response, logs, or any store
  msp360-mcp -> Agent: {"authenticated": true, "expires_in": N|null}
                      | structured error envelope (unauthorized | upstream_error | ...)
```

### Non-functional

- **Idempotency & concurrency**: The tool is naturally idempotent — every call is an independent,
  fresh vendor login, with no local state carried between calls (no cache to get out of sync, no
  "already logged in" branch). This sidesteps AC4's multi-tenant requirement almost entirely: because
  nothing is cached or shared across requests, there is no mechanism by which one tenant's call could
  affect another's.
- **Performance**: One outbound call per invocation; no batching concerns. Outbound timeouts: 5s
  connect / 30s read (SOP §5); single call budget well under the 120s SOP ceiling.
- **Security**: Credentials read only from `X-Msp360-Username`/`X-Msp360-Password` headers, never an
  env-var fallback (SOP §3.1); request-scoped via `contextvars.ContextVar` with `finally`-reset (SOP
  §3.3); the vendor's `access_token` is read only long enough to extract `expires_in` and is never
  logged, stored, or returned (AC5) — this is the one line of code in the whole tool that needs a
  code-review-level guarantee, and is called out explicitly for the reviewer in Self-test.
- **Multi-tenant isolation**: Every request carries its own tenant's MSP360 credentials in headers;
  this service never caches or shares anything keyed by credential, so there is no cross-tenant
  leakage surface to defend (AC4). This is a stronger guarantee than a cached-token design would give,
  at the cost of one extra vendor login call per invocation — acceptable since this tool is a
  connectivity check, not something called in a hot loop.
- **Observability**: One structured log line per call — tool name, outcome (`authenticated` /
  `unauthorized` / `upstream_error`), MSP360 HTTP status code, latency. Never the username, password,
  or access_token (AC5, SOP §6/§11).

### Rollout & rollback

No feature flag — brand-new tool, nothing regresses by shipping it. `msp360-mcp` is not yet
registered as a vendor on INT (confirmed: no prior deploy/register for this repo exists). Whichever of
the seven MSP360 tickets' dev work reaches `main` and calls the publish API first must use
`mcppub register` (new-vendor first registration, per `references/mcp-track.md` §4.8), not
`mcppub publish`; every ticket after that first one uses `publish`. This ticket's dev/review legs
should check INT-registration status before choosing which call to make, rather than assuming based
on ticket number order. Rollback is simply not calling the tool; it has no data footprint to reverse.

### Test strategy

Unit tests only, no real MSP360 account required (`references/mcp-track.md` §2.5 — missing a vendor
test account is not a blocker): mock `httpx` responses for 200 (with and without `expires_in`), 401,
403, 429, 500, and a timeout; one middleware test for the missing-header path; one test that asserts

  false, ...}}`.

  `unauthorized`/`retryable: false` envelope as TC3.
- **TC5** (AC3): Given the request is missing `X-Msp360-Password`, when `msp360_provider_login` is
  called, then the server responds HTTP 401 listing the required headers, and no HTTP call to MSP360
  is made (assert the mocked vendor client was never invoked).
- **TC6** (AC4): Given two concurrent requests with different credentials (tenant A invalid, tenant B
  valid), when both are in flight at once, then tenant A's result is `unauthorized` and tenant B's is
  `authenticated: true` — neither result is swapped or shared.
- **TC7** (AC5): Given a mocked vendor 200 response containing a distinctive `access_token` value,
  when `msp360_provider_login` is called and its response and all captured log output are searched
  for that exact string, then it is not found anywhere.
- **TC8** (AC6): Given the vendor login call times out or returns a 5xx response, when
  `msp360_provider_login` is called, then the result is `{"error": {"code": "upstream_error",
  "retryable": true, ...}}`.
