## Requirement understanding

One line: Add an MSP360 Managed Backup connector/MCP with a msp360_list_users tool that lists MSP360 backup users, each representing one or more backup endpoints/computers (gap found in the EMD Networking Services Rewst "MSP360" flow, 29 runs/365d, evidence grade A; mspbots-gap-register.xlsx item 40).

The ticket is one of six sibling "tool" tickets (PRD-21604–21609) that migrate specific steps of an
existing Rewst automation for client EMD Networking Services into Agent-platform MCP tools. In the
original Rewst flow, `custom.generic_request` calls `GET /api/Users` with
`Authorization: Bearer {{ CTX.authentication_response.access_token }}` — the token obtained by the
login step sibling ticket PRD-21604 already designed as `msp360_provider_login`. This ticket is the
next step in that same migrated flow: give the Agent a tool that returns the list of MSP360 "backup
users" (MSP360's own grouping of one or more backup endpoints/computers under one account), without
the Agent ever having to hold or pass a bearer token itself.

## Product design

### Goals / Non-goals

**Goals** (this ticket only):
- An Agent can list the MSP360 backup users visible to the connected MSP360 provider account, using
  the exact vendor call the gap register names (`GET /api/Users`), so the Rewst-to-MSPbots mapping for
  this gap-register line item stays traceable.
- The tool follows this repo's already-fixed header-credential pattern (`X-Msp360-Username` /
  `X-Msp360-Password`, identical names to PRD-21273/PRD-21604/PRD-21605) and its cached-login
  `api_client.py` pattern (internal login via a shared, cached helper — not a token handed to the
  Agent), the same shape PRD-21605 already chose for the same reason (a second vendor call follows
  login).
- The returned list is capped and paginated per the platform's token-economy rule (SOP §2.5), even
  though the vendor endpoint itself has no pagination — so a provider account with many backup users
  cannot blow past the response-size ceiling.

**Non-goals** (explicitly out of scope for this ticket):
- Reading, creating, updating, or deleting an individual user's details — the ticket only asks for the
  list view; the vendor's `DestinationList` nested detail and any single-user endpoint are not built
  here.
- Listing a user's computers (`GET /api/Users/{userId}/Computers`) — PRD-21607 owns that, as a
  separate drill-down tool keyed off this tool's `user_id` output.
- Listing companies, packages, or domains — PRD-21605/21608/21609 own those, respectively.
- Backup-health monitoring or plan start/stop, and the `msp360_provider_login` connectivity-check tool
  — PRD-21273 and PRD-21604 own those, respectively; zero overlap.
- Exposing `FirstName`/`LastName`/`NotificationEmails`/`LicenseManagmentMode`/`DestinationList` — none
  of these are in the ticket's own field list (`ID`, `Email`, `Company`, `Enabled`, `SpaceUsed`); per
  SOP §2.5's field-trimming rule, fields the ticket/Rewst flow does not use are dropped rather than
  passed through. `LicenseManagmentMode`'s enum values are not documented anywhere found during this
  design (see Open questions, OQ1) — not exposing it at all avoids guessing at a mapping no source
  confirms.

### Acceptance criteria

- **AC1**: Given valid MSP360 provider credentials are supplied in the connector's headers and at
  least one backup user exists under that provider account, When the Agent calls
  `msp360_list_users`, Then it receives `{"users": [{"user_id", "email", "company", "enabled",
  "space_used_kb"}, ...], "count": N, "has_more": false}` where `count` equals the number of items in
  `users`, and no item contains any field other than those five.
- **AC2 (empty is not an error)**: Given valid credentials and zero backup users exist under that
  provider account, When the Agent calls `msp360_list_users`, Then it receives `{"users": [], "count":
  0, "has_more": false}` — not a `not_found` error (SOP §4.2's "empty is not `not_found`" rule).
- **AC3**: Given the MSP360 provider credentials are rejected by the vendor (wrong password, revoked
  API credential), When the Agent calls `msp360_list_users`, Then it receives a structured error
  envelope with `code: "unauthorized"` and `retryable: false` — never a raw exception, stack trace, or
  HTTP 500.
- **AC4**: Given the request to the MCP server is missing one or both required credential headers,
  When the Agent calls `msp360_list_users`, Then the server returns HTTP 401 with a body listing which
  header(s) are required, and does not attempt a call to MSP360 at all.
- **AC5 (multi-tenant)**: Given two different MSPbots tenants call `msp360_list_users` concurrently
  with two different sets of credentials (each provider account having a different user list), When
  both requests are in flight at the same time, Then each tenant's response contains only that
  tenant's own backup users — no user, credential, or cached token is ever attributable to another
  tenant's request.
- **AC6 (security)**: Given any outcome of `msp360_list_users` (success, rejected credentials, or an
  upstream error), When the tool returns its result or the server writes a log line for the call, Then
  neither the submitted password nor the vendor's `access_token` ever appears in the tool's response
  body or in any log output.
- **AC7 (pagination)**: Given a provider account with more backup users than the tool's default
  `limit`, When the Agent calls `msp360_list_users` with no `limit` argument, Then at most 50 users are
  returned and `has_more: true` is set; When the Agent calls it with `limit` set above the hard cap of
  200, Then at most 200 are returned (the hard cap wins); When the serialized result would exceed
  20,000 characters before either limit is hit, Then the result is truncated at whichever bound is hit
  first and `has_more: true` is set (SOP §2.5's "character cap wins" rule).
- **AC8 (resilience)**: Given MSP360's `/api/Users` endpoint is unreachable, times out, or returns a
  5xx response, When the Agent calls `msp360_list_users`, Then it receives a structured error with
  `code: "upstream_error"` and `retryable: true`, not an unhandled exception.
- **AC9 (disabled users are not filtered)**: Given a provider account with both enabled and disabled
  backup users, When the Agent calls `msp360_list_users` with no filter, Then both are returned with
  their actual `enabled` value — the tool never silently hides disabled users, since the ticket's own
  field list includes `Enabled` precisely so the Agent (or a human reading its output) can see that
  state.

### Open questions

- **[non-blocking, assumption] OQ1**: `LicenseManagmentMode`'s enum values (`UserModeType`) are not
  documented with labels anywhere this design found, mirroring PRD-21605's OQ3 for
  `LicenseSettings`. **Resolution**: this field is not in the ticket's own field list, so it is simply
  not exposed by this tool (see Non-goals) — no mapping needs to be guessed. If a future ticket needs
  it, that ticket adds the field with whatever mapping it can confirm at that time; this design does
  not block on it.
- **[non-blocking, assumption] OQ2**: `Company` is documented as a plain string field on the user
  object, not a company id. **Assumption**: it is the company's display name, and is not guaranteed to
  be an exact string match against `msp360_list_companies`' (PRD-21605) `name` field returned from a
  different endpoint (`GET /api/Companies`) — the two endpoints may format or capitalize names
  differently, and MSP360's docs do not state they are the same string. This tool exposes `company`
  verbatim as the vendor returns it; it does not attempt to resolve or cross-reference it against
  PRD-21605's company list. If vendor behavior in a live account shows the two values differ for the
  same company, that is a UX note for the Agent prompt layer, not a defect in either tool's contract.
- **[non-blocking, not this ticket's call to make] OQ3**: This design reuses `dev/PRD-21273`'s /
  `dev/PRD-21605`'s cached-login `api_client.py` shape (see Tech design · Option analysis) rather than
  building a second, independent login/cache implementation. If, by the time this ticket's dev leg
  runs, none of PRD-21273/PRD-21604/PRD-21605 has landed in `main` yet, this ticket's dev leg becomes a
  first mover and should build the cached-login shape itself (consistent with PRD-21273's own design,
  which anticipates exactly this coordination scenario via the repo's `dev-lock`) rather than inventing
  a different one.

## Tech design

### Conclusion

Add one new tool, `msp360_list_users`, to the `msp360-mcp` service skeleton (Python 3.12 + uv +
FastMCP, per the vendor-mcp-development SOP's reference layout) — building the skeleton if none of the
three sibling tickets' dev work has landed yet, or extending it (adding one function to
`api_client.py` and one new `tools/users.py`) if it has. The tool takes optional `limit`/`offset`,
calls `GET https://api.mspbackups.com/api/Users` using a bearer token obtained (and cached) via the
same login helper PRD-21273's and PRD-21605's tools use, and maps the result to a trimmed, paginated
JSON object or a structured error.

### Data & API contract

**Header credentials** (identical to the three sibling designs — same repo, same connector, must not
diverge):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Msp360-Username` | Yes | MSP360 Managed Backup provider-account username | MSP360 admin portal → Settings → API credentials |
| `X-Msp360-Password` | Yes | MSP360 Managed Backup provider-account password | Same as above |

**Vendor calls** (inside `api_client.py`):

```
POST https://api.mspbackups.com/api/Provider/Login     (via the shared, cached login() helper)
  body: {"UserName": "<from header>", "Password": "<from header>"}
  200 -> {"access_token": "...", "expires_in": <seconds>}
  401/403 -> credentials rejected

GET  https://api.mspbackups.com/api/Users               (Authorization: Bearer <token>)
  200 -> [ {"ID": "<string>", "Email": "...", "FirstName": "...", "LastName": "...",
            "NotificationEmails": [...], "Company": "...", "Enabled": <bool>,
            "LicenseManagmentMode": <enum, undocumented values>, "SpaceUsed": <int, KB>,
            "DestinationList": [...]} ]
  401/403 -> token rejected (one reactive retry with a refreshed token, then unauthorized — same
             retry policy the sibling designs already specify)
  5xx / timeout -> upstream error
```

**Tool contract** (Agent-facing, returned as a compact JSON string per SOP §4.1):

```
msp360_list_users(limit?: int = 50, offset?: int = 0)
  -> {"users": [{"user_id", "email", "company", "enabled", "space_used_kb"}],
      "count": N, "has_more": bool}
```

Only the five fields the ticket names are exposed (`ID`→`user_id`, `Email`→`email`,
`Company`→`company`, `Enabled`→`enabled`, `SpaceUsed`→`space_used_kb`) — `FirstName`, `LastName`,
`NotificationEmails`, `LicenseManagmentMode`, `DestinationList` are dropped per SOP §2.5's
field-trimming rule, since neither the ticket nor the Rewst flow it migrates uses them. The `_kb`
suffix on `space_used_kb` is kept rather than converted to bytes, because the vendor's own
documentation states the unit as KB explicitly (unlike PRD-21605's `storage_limit_bytes`, whose unit
had to be assumed) — converting units the vendor already states plainly would introduce a conversion
bug risk for no benefit. `limit` default 50 / hard cap 200 (SOP §2.5); since the vendor endpoint has no
server-side pagination, the connector fetches the full vendor list once and applies `limit`/`offset`
client-side; if the trimmed, paginated result would still exceed 20,000 characters, truncate further
and set `has_more=true` (character cap wins, AC7).

**Error envelope** (SOP §4.2):

| Vendor / server condition | `code` | `retryable` |
|---|---|---|
| Missing `X-Msp360-Username` and/or `X-Msp360-Password` header | *(HTTP 401 from middleware, before any tool-level envelope — AC4)* | n/a |
| Login call (`/api/Provider/Login`) returns 401/403 | `unauthorized` | false |
| `/api/Users` returns 401/403 after one retry-with-refreshed-token | `unauthorized` | false |
| Vendor returns 400/422 (defensive mapping — not expected, this endpoint takes no input) | `invalid_argument` | false |
| Vendor returns 429 | `rate_limited` | true |
| Vendor returns 5xx, or connect/read timeout | `upstream_error` | true |
| Anything else unexpected | `upstream_error` | true |

Zero users is a normal successful result (AC2), never `not_found` — `not_found` is reserved for "fetch
a specific resource by id that doesn't exist," which this list-only tool never does.

**Backward compatibility**: N/A — brand-new tool. Tool name uses the `msp360_` prefix so it cannot
collide with any other vendor's tools in the same Agent session, or with this repo's other tools
(`msp360_provider_login`, `msp360_list_companies`, PRD-21273's six, and the three other gap-register
tools still to be designed).

### Key flow / sequence

```
Agent -> Gateway -> msp360-mcp: msp360_list_users(limit?, offset?)
  msp360-mcp: read X-Msp360-Username / X-Msp360-Password from the request (middleware);
              missing either -> 401, do not call the vendor (AC4)
  msp360-mcp -> api_client.login(): cached token for (username, password), or a fresh
                POST /api/Provider/Login if absent/expired
  msp360-mcp -> MSP360 API: GET /api/Users  (Authorization: Bearer <token>)
  MSP360 API -> msp360-mcp: 200 [User, ...]  |  401/403  |  5xx/timeout
  msp360-mcp: trim each item to {user_id, email, company, enabled, space_used_kb};
              apply limit/offset and the 20,000-character cap (whichever binds first);
              discard the raw access_token from memory once the call completes
  msp360-mcp -> Agent: {"users": [...], "count": N, "has_more": bool}
                      | structured error envelope (unauthorized | upstream_error | ...)
```

### Non-functional

- **Idempotency & concurrency**: Read-only, naturally idempotent — repeated calls with the same
  `limit`/`offset` return the same users (modulo upstream changes). The shared token cache is keyed
  per `(username, password)`, not per tenant id, but since each tenant supplies its own distinct
  credential pair, this is equivalent to per-tenant isolation in practice (AC5) — the same isolation
  argument PRD-21273's and PRD-21605's designs already make for their own tools sharing the same cache.
- **Performance**: One cached-or-fresh login call plus one list call per invocation in the worst case
  (cache miss); one list call in the common case (cache hit). Outbound timeouts: 5s connect / 30s read
  (SOP §5), consistent with the sibling designs in this repo.
- **Security**: Credentials read only from `X-Msp360-Username`/`X-Msp360-Password` headers, never an
  env-var fallback (SOP §3.1); the vendor's `access_token` lives only inside `api_client.py`'s cache
  (keyed on the credential pair, never logged, never returned to a tool caller) and is never passed to
  or through `tools/users.py` beyond using it as a bearer header on the one outbound call (AC6).
- **Multi-tenant isolation**: Every request carries its own tenant's MSP360 credentials in headers; the
  shared cache's key is the credential pair itself, so two tenants with different credentials never
  share a cache entry, and a request's response is built only from that request's own vendor call
  (AC5).
- **Observability**: One structured log line per call — tool name, outcome (`ok` / `unauthorized` /
  `upstream_error`), MSP360 HTTP status code, latency, result count. Never the username, password, or
  access_token (AC6, SOP §6/§11).
