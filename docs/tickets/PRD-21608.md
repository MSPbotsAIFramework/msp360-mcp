MCP tools. In the original Rewst flow, `custom.generic_request` calls `GET API/Packages` with a
bearer token obtained by the login step (PRD-21604's `msp360_provider_login`). This ticket is the
next step: give the Agent a tool that lists the storage/license packages configured on the connected
MSP360 provider account — a distinct resource from backup plans, company records, or users.

## Product design

### Goals / Non-goals

**Goals** (this ticket only):
- An Agent can list the storage/license packages configured on the connected MSP360 provider
  account — the catalog MSP360 uses to allocate storage/restore quotas and cost to customers — in one
  tool call, matching the Rewst flow this ticket migrates (`GET API/Packages`).
- The connector follows the same connect-once / Header-credential pattern as every other MSPbots
  connector and this repo's other sibling tools (wiki: `ProductDocs/15-Capabilities.md` §
  "Connection forms") — no custom UI.

**Non-goals** (explicitly out of scope, left to sibling tickets or not asked for):
- Creating, editing, or deleting packages (`POST`/`PUT`/`DELETE API/Packages`) — the ticket only asks
  to list.
- Listing companies, backup users, or user-computers — PRD-21605/21606/21607 own those.
- Backup-plan monitoring or start/stop — PRD-21273 owns that (its own Non-goals list names this
  ticket as the package owner, confirming no overlap).
- Domain/app listing — PRD-21609.
- Assigning a package to a company/user, or any license-management action — not asked for; this is a
  read-only catalog listing.

### Acceptance criteria

- **AC1**: Given valid MSP360 credentials are connected, When the Agent calls
  `msp360_list_packages`, Then it receives every configured package with its id, name, cost,
  storage limit, restore limit, and enabled flag.
- **AC2**: Given the account has zero packages configured, When the tool is called, Then the result
  is an empty list, not an error.
- **AC3**: Given the connected MSP360 account's credentials are wrong or expired, When the tool is
  called, Then it returns a structured `unauthorized` error — it never retries indefinitely nor
  silently returns stale/cached data.
- **AC4**: Given a request to the MCP server is missing a required credential header, When the tool
  is called, Then the server responds with an auth failure before any call reaches MSP360.
- **AC5 (multi-tenant)**: Given two different MSPbots tenants each connect their own MSP360 account,
  When tenant A calls this tool, Then only tenant A's packages are ever returned — the server must
  not reuse tenant B's cached token or data for tenant A's request, even under concurrent load (this
  is a platform-wide MCP contract, not special to MSP360, but it is the AC the multi-tenant test case
  in Test cases exists to pin down).
- **AC6**: Given the tool's response and all logging, When any call is made (success or failure),
  Then the raw MSP360 password or bearer token is never present in the tool's output or in any log
  line.
- **AC7**: Given the vendor endpoint has no server-side pagination and an account can have many
  packages, When the tool is called, Then the result is capped (default 50, hard cap 200 regardless
  of the requested limit, and further capped if the serialized result would exceed 20,000 characters)
  and `has_more` reflects whether more packages exist beyond the returned page.
- **AC8**: Given the vendor call returns a 5xx response or times out, When the tool is called, Then
  it returns a structured `upstream_error` with `retryable: true`, not a raw exception.
- **AC9**: Given the account has both enabled and disabled packages, When the tool is called, Then
  both are returned (the tool does not silently filter out disabled packages) — the Agent sees the
  `enabled` flag per package and decides what to do with it. (Same call PRD-21606 made for disabled
  users; same reasoning: the ticket's own field list didn't ask for an `enabled` filter, and
  silently hiding disabled packages would hide information the Agent might need.)

### Open questions

None blocking. The one genuine unknown at this design pass — whether MSP360 enforces any
provider-account-level limit on package count that would make the hard cap in AC7 bite in practice —
does not change the tool's contract either way (the cap is a platform-side token-economy rule per the
vendor-mcp-development SOP §2.5, not a vendor-specific assumption), so it is not listed as an open
question requiring product input.

## Tech design

### Conclusion

Add one new MCP tool, `msp360_list_packages`, to the shared `msp360-mcp` repo. Reuse the
`api_client.py` cached-login shape from PRD-21273/PRD-21605 (not PRD-21604's no-cache variant), add a
`list_packages()` vendor call, and expose it as a trimmed, paginated, snake_case tool contract
following this repo's established conventions. This is the cheapest correct design because the single
asked-for capability maps directly onto one already-documented REST call (confirmed via live vendor
Swagger) with no new data model, no migration, and no multi-step process to invent — the only
engineering cost specific to this ticket is the one new tool module plus whatever shared scaffold
files are still missing if this ticket's dev leg happens to land first among the unmerged siblings.

### Data & API contract

**Header credentials** (identical to every sibling's design — same repo, same connector, must not
diverge):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Msp360-Username` | Yes | MSP360 Managed Backup provider-account username | MSP360 admin portal → Settings → API credentials |
| `X-Msp360-Password` | Yes | MSP360 Managed Backup provider-account password | Same as above |

**Vendor call** (inside `api_client.py`):

```
POST https://api.mspbackups.com/api/Provider/Login     (via the shared, cached login() helper)
  body: {"UserName": "<from header>", "Password": "<from header>"}
  200 -> {"access_token": "...", "expires_in": <seconds>}
  401/403 -> credentials rejected

GET  https://api.mspbackups.com/api/Packages            (Authorization: Bearer <token>)
  200 -> [ {"ID": <int32>, "Name": "...", "Cost": <double>, "StorageLimit": <double, Gb>,
            "RestoreLimit": <double, Gb>, "Description": "...", "Enabled": <bool>,
            "isGlacierRestoreLimit": <bool>, "UseRestoreLimit": <bool>,
            "GlacierRestoreType": <int32 enum>} ]
  401/403 -> token rejected (one reactive retry with a refreshed token, then unauthorized — same
             retry policy PRD-21273's `api_client.py` already specifies)
  5xx / timeout -> upstream error
```

**Tool contract** (Agent-facing, returned as a compact JSON string per SOP §4.1):

```
msp360_list_packages(limit?: int = 50, offset?: int = 0)
  -> {"packages": [{"package_id", "name", "cost", "storage_limit_gb", "restore_limit_gb",
                     "enabled"}],
      "count": N, "has_more": bool}
```

Mapped fields: `ID`→`package_id`, `Name`→`name`, `Cost`→`cost`, `StorageLimit`→`storage_limit_gb`,
`RestoreLimit`→`restore_limit_gb`, `Enabled`→`enabled`. Dropped per SOP §2.5 field-trimming:
`Description` (free-text, not used by the ticket's Rewst flow or ask), `isGlacierRestoreLimit`,
`UseRestoreLimit`, `GlacierRestoreType` (backup-engine-internal fields unrelated to "list packages").
`limit` default 50 / hard cap 200 (SOP §2.5); since the vendor endpoint has no server-side pagination,
the connector fetches the full vendor list once and applies `limit`/`offset` client-side; if the
trimmed, paginated result would still exceed 20,000 characters, truncate further and set
`has_more=true` (character cap wins, AC7).

**Error envelope** (SOP §4.2):

| Vendor / server condition | `code` | `retryable` |
|---|---|---|
| Missing `X-Msp360-Username` and/or `X-Msp360-Password` header | *(auth failure from middleware, before any tool-level envelope — AC4)* | n/a |
| Login call (`/api/Provider/Login`) returns 401/403 | `unauthorized` | false |
| `/api/Packages` returns 401/403 after one retry-with-refreshed-token | `unauthorized` | false |
| Vendor returns 400/422 (defensive mapping — not expected, this endpoint takes no input) | `invalid_argument` | false |
| Vendor returns 429 | `rate_limited` | true |
| Vendor returns 5xx, or connect/read timeout | `upstream_error` | true |
| Anything else unexpected | `upstream_error` | true |

Zero packages is a normal successful result (AC2), never `not_found` — this endpoint takes no id
argument, so there is no "resource not found" case for a list-only tool.

**Backward compatibility**: N/A — brand-new tool. `msp360_` prefix prevents collision with any other
vendor's tools, or with this repo's other tools (`msp360_provider_login`, PRD-21273's six, and the
sibling list tools).

### Key flow / sequence

```
Agent -> Gateway -> msp360-mcp: msp360_list_packages()
  msp360-mcp: have a cached, non-expired token for this credential fingerprint? use it.
              else: POST /api/Provider/Login with Header creds -> cache (token, expiry)
  msp360-mcp -> MSP360 API: GET /api/Packages  (Authorization: Bearer <token>)
  MSP360 API -> msp360-mcp: [ {ID, Name, Cost, StorageLimit, RestoreLimit, Enabled, ...}, ... ]
  msp360-mcp: trim/rename fields, apply limit/offset, cap at 200/20000 chars, set has_more
  msp360-mcp -> Agent: {"packages": [...], "count", "has_more"}
```

### Non-functional

- **Idempotency & concurrency**: Read-only `GET` call — idempotent and side-effect-free by
  construction; safe to retry. No local state kept per call beyond the shared in-memory token cache
  (keyed by credential fingerprint, with expiry — same permitted exception every sibling ticket uses).
- **Performance**: Vendor endpoint has no server-side pagination, so a provider account with many
  packages means one full fetch per call. Hard cap of 200 records / 20,000 serialized characters
  (whichever hits first); `has_more` tells the Agent to narrow with `offset` rather than assume
  completeness. Outbound timeouts: 5s connect / 30s read (SOP §5); single call budget < 120s including
  retries.
- **Security**: Credentials only ever read from `X-Msp360-Username`/`X-Msp360-Password` headers, never
  an env-var fallback (SOP §3.1); request-scoped via `contextvars.ContextVar` with `finally`-reset (SOP
  §3.3); token cache keyed by `(username, password)` fingerprint only, never shared across distinct
  credential pairs (SOP §3.4); no credential or vendor-response body ever logged (SOP §6, §11).
- **Multi-tenant isolation**: Every request carries its own tenant's MSP360 credentials in Headers; the
  Gateway keeps tenant A's and tenant B's calls apart at the transport level — this service's only
  obligation (and the one AC5 pins down) is to never let one request's cached token leak into another
  credential fingerprint's lookup, which the `(username, password)` cache key already guarantees by
  construction (same mechanism, and same guarantee, as every sibling tool in this repo).
- **Observability**: Structured log per call — tool name, requested `limit`/`offset`, MSP360 status
  code, latency, mapped error `code`, returned `count`/`has_more`. No vendor response bodies logged in
  full (package `Description` is free text and is not logged — SOP §6, §11).
