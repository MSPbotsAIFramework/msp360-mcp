## Requirement understanding

One line: Add an MSP360 Managed Backup connector/MCP with a msp360_list_companies tool that lists the customer companies in MSP360 (gap found in the EMD Networking Services Rewst "MSP360" flow, 29 runs/365d, evidence grade A; mspbots-gap-register.xlsx item 39).

The ticket is one of six sibling "tool" tickets (PRD-21604–21609) that migrate specific steps of an
existing Rewst automation for client EMD Networking Services into Agent-platform MCP tools. In the
original Rewst flow, `custom.generic_request` calls `GET /API/Companies` with
`Authorization: Bearer {{ CTX.authentication_response.access_token }}` — the token obtained by the
login step that sibling ticket PRD-21605's predecessor, PRD-21604, already designed as
`msp360_provider_login`. This ticket is the next step in that same flow: give the Agent a tool that
returns the list of MSP360 customer companies, without the Agent ever having to hold or pass a bearer
token itself.

## Product design

### Goals / Non-goals

**Goals** (this ticket only):
- An Agent can list the MSP360 customer companies visible to the connected MSP360 provider account,
  using the exact vendor call the gap register names (`GET /api/Companies`), so the Rewst-to-MSPbots
  mapping for this gap-register line item stays traceable.
- The tool follows this repo's already-fixed header-credential pattern (`X-Msp360-Username` /
  `X-Msp360-Password`, identical names to PRD-21604 and PRD-21273) and its token-handling pattern
  (internal login via a shared, cached `api_client.py` helper — not a token handed to the Agent).
- The returned list is capped and paginated per the platform's token-economy rule (SOP §2.5), even
  though the vendor endpoint itself has no pagination — so a provider account with a very large
  company count cannot blow past the response-size ceiling.

**Non-goals** (explicitly out of scope for this ticket):
- Reading or writing an individual company's details (`GET`/`PUT`/`POST`/`DELETE
  /api/Companies/{id}`) — the ticket only asks for the list view; a single-company read/write tool is
  not named in the gap register and is not built here.
- Listing users, user-computers, packages, or domains — PRD-21606/21607/21608/21609 own those,
  respectively.
- Backup-health monitoring or plan start/stop, and the `msp360_provider_login` connectivity-check
  tool — PRD-21273 and PRD-21604 own those, respectively; zero overlap.
- Any company-level write operation (create/update/delete a company) — the vendor API supports these,
  but neither the gap register item nor the Rewst flow calls them; adding write tools without a named
  need would be scope creep into destructive territory this ticket has no mandate for.

### Acceptance criteria

- **AC1**: Given valid MSP360 provider credentials are supplied in the connector's headers and at
  least one company exists under that provider account, When the Agent calls
  `msp360_list_companies`, Then it receives `{"companies": [{"company_id", "name",
  "storage_limit_bytes", "license_settings"}, ...], "count": N, "has_more": false}` where `count`
  equals the number of items in `companies`, and no item contains any field other than those four.
- **AC2 (empty is not an error)**: Given valid credentials and zero companies exist under that
  provider account, When the Agent calls `msp360_list_companies`, Then it receives `{"companies": [],
  "count": 0, "has_more": false}` — not a `not_found` error (SOP §4.2's "empty is not `not_found`"
  rule).
- **AC3**: Given the MSP360 provider credentials are rejected by the vendor (wrong password, revoked
  API credential), When the Agent calls `msp360_list_companies`, Then it receives a structured error
  envelope with `code: "unauthorized"` and `retryable: false` — never a raw exception, stack trace, or
  HTTP 500.
- **AC4**: Given the request to the MCP server is missing one or both required credential headers,
  When the Agent calls `msp360_list_companies`, Then the server returns HTTP 401 with a body listing
  which header(s) are required, and does not attempt a call to MSP360 at all.
- **AC5 (multi-tenant)**: Given two different MSPbots tenants call `msp360_list_companies`
  concurrently with two different sets of credentials (each provider account having a different
  company list), When both requests are in flight at the same time, Then each tenant's response
  contains only that tenant's own companies — no company, credential, or cached token is ever
  attributable to another tenant's request.
- **AC6 (security)**: Given any outcome of `msp360_list_companies` (success, rejected credentials, or
  an upstream error), When the tool returns its result or the server writes a log line for the call,
  Then neither the submitted password nor the vendor's `access_token` ever appears in the tool's
  response body or in any log output.
- **AC7 (pagination)**: Given a provider account with more companies than the tool's default `limit`,
  When the Agent calls `msp360_list_companies` with no `limit` argument, Then at most 50 companies are
  returned and `has_more: true` is set; When the Agent calls it with `limit` set above the hard cap of
  200, Then at most 200 are returned (the hard cap wins); When the serialized result would exceed
  20,000 characters before either limit is hit, Then the result is truncated at whichever bound is hit
  first and `has_more: true` is set (SOP §2.5's "character cap wins" rule).
- **AC8 (resilience)**: Given MSP360's `/api/Companies` endpoint is unreachable, times out, or returns
  a 5xx response, When the Agent calls `msp360_list_companies`, Then it receives a structured error
  with `code: "upstream_error"` and `retryable: true`, not an unhandled exception.

### Open questions

  `api.mspbackups.com/help/v2/swagger`, fetched 2026-11-03) names the id field `Id`, not `CompanyID` as
  the ticket's description calls it. **Assumption**: this is the same field the ticket means (a
  provider-scoped company identifier), just named differently in the vendor's own schema vs. the gap
  register's paraphrase; the tool exposes it as `company_id` (the ticket's intended name, in the
  connector's own snake_case convention) sourced from the vendor's `Id` field. If this assumption is
  wrong — i.e., there is a genuinely separate `CompanyID` field the Swagger excerpt did not surface —
  only `api_client.py`'s field mapping changes, not the tool's contract or this design's other
  sections. Dev should confirm against a live MSP360 response if a test account becomes available and
  record what was actually seen in Self-test.
- **[non-blocking, assumption] OQ2**: Neither the ticket description nor the live Swagger excerpt
  states `StorageLimit`'s unit. **Assumption**: treat it as an integer and expose it verbatim as
  `storage_limit_bytes`, the common MSP360-ecosystem convention for this field; if the unit turns out

  presence or type.
- **[non-blocking, assumption] OQ3**: `LicenseSettings`'s enum values (0, 1, 2 per Swagger) are not
  documented with labels anywhere this design found. **Assumption**: pass the raw integer through
  rather than guessing at label names that could be wrong; if MSP360 publishes or a live account
  reveals the mapping, a label field can be added later without breaking the existing integer field
  (additive, not a breaking change — SOP §13).
- **[non-blocking, not this ticket's call to make] OQ4**: This design reuses `dev/PRD-21273`'s

  PRD-21273 nor PRD-21604 has landed in `main` yet, this ticket's dev leg becomes a first mover and

### Data & API contract

**Header credentials** (identical to PRD-21273's and PRD-21604's designs — same repo, same connector,
must not diverge):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Msp360-Username` | Yes | MSP360 Managed Backup provider-account username | MSP360 admin portal → Settings → API credentials |
| `X-Msp360-Password` | Yes | MSP360 Managed Backup provider-account password | Same as above |

**Vendor calls** (inside `api_client.py`):

```
POST https://api.mspbackups.com/api/Provider/Login     (via the shared, cached login() helper)
  body: {"UserName": "<from header>", "Password": "<from header>"}
  200 -> {"access_token": "...", "expires_in": <seconds>}
  401/403 -> credentials rejected

GET  https://api.mspbackups.com/api/Companies           (Authorization: Bearer <token>)
  200 -> [ {"Id": "<uuid>", "Name": "...", "StorageLimit": <int64>, "LicenseSettings": <0|1|2>,
            "Destinations": [...], "DefaultLicense": <int>, "AllowedLicenses": [...]} ]
  401/403 -> token rejected (one reactive retry with a refreshed token, then unauthorized — same
             retry policy PRD-21273's api_client.py already specifies)
  5xx / timeout -> upstream error
```

**Tool contract** (Agent-facing, returned as a compact JSON string per SOP §4.1):

```
msp360_list_companies(limit?: int = 50, offset?: int = 0)
  -> {"companies": [{"company_id", "name", "storage_limit_bytes", "license_settings"}],
      "count": N, "has_more": bool}
```

Only the four fields the ticket names are exposed (`Id`→`company_id`, `Name`→`name`,
`StorageLimit`→`storage_limit_bytes`, `LicenseSettings`→`license_settings`) — `Destinations`,
`DefaultLicense`, `AllowedLicenses` are dropped per SOP §2.5's field-trimming rule, since neither the
ticket nor the Rewst flow it migrates uses them. `limit` default 50 / hard cap 200 (SOP §2.5); since
the vendor endpoint has no server-side pagination, the connector fetches the full vendor list once and
applies `limit`/`offset` client-side; if the trimmed, paginated result would still exceed 20,000
characters, truncate further and set `has_more=true` (character cap wins, AC7).

**Error envelope** (SOP §4.2):

| Vendor / server condition | `code` | `retryable` |
|---|---|---|
| Missing `X-Msp360-Username` and/or `X-Msp360-Password` header | *(HTTP 401 from middleware, before any tool-level envelope — AC4)* | n/a |
| Login call (`/api/Provider/Login`) returns 401/403 | `unauthorized` | false |
| `/api/Companies` returns 401/403 after one retry-with-refreshed-token | `unauthorized` | false |
| Vendor returns 400/422 (defensive mapping — not expected, this endpoint takes no input) | `invalid_argument` | false |
| Vendor returns 429 | `rate_limited` | true |
| Vendor returns 5xx, or connect/read timeout | `upstream_error` | true |
| Anything else unexpected | `upstream_error` | true |

Zero companies is a normal successful result (AC2), never `not_found` — `not_found` is reserved for
"fetch a specific resource by id that doesn't exist," which this list-only tool never does.

**Backward compatibility**: N/A — brand-new tool. Tool name uses the `msp360_` prefix so it cannot
collide with any other vendor's tools in the same Agent session, or with this repo's other tools
(`msp360_provider_login`, PRD-21273's six, and the four other gap-register tools still to be designed).

### Key flow / sequence

```
Agent -> Gateway -> msp360-mcp: msp360_list_companies(limit?, offset?)
  msp360-mcp: read X-Msp360-Username / X-Msp360-Password from the request (middleware);
              missing either -> 401, do not call the vendor (AC4)
  msp360-mcp -> api_client.login(): cached token for (username, password), or a fresh
                POST /api/Provider/Login if absent/expired
  msp360-mcp -> MSP360 API: GET /api/Companies  (Authorization: Bearer <token>)
  MSP360 API -> msp360-mcp: 200 [CompanyModel, ...]  |  401/403  |  5xx/timeout
  msp360-mcp: trim each item to {company_id, name, storage_limit_bytes, license_settings};
              apply limit/offset and the 20,000-character cap (whichever binds first);
              discard the raw access_token from memory once the call completes
  msp360-mcp -> Agent: {"companies": [...], "count": N, "has_more": bool}
                      | structured error envelope (unauthorized | upstream_error | ...)
```

### Non-functional

- **Idempotency & concurrency**: Read-only, naturally idempotent — repeated calls with the same
  `limit`/`offset` return the same companies (modulo upstream changes). The shared token cache is
  keyed per `(username, password)`, not per tenant id, but since each tenant supplies its own distinct
  credential pair, this is equivalent to per-tenant isolation in practice (AC5) — this is the same
  isolation argument PRD-21273's design already makes for its own six tools sharing the same cache.
- **Performance**: One cached-or-fresh login call plus one list call per invocation in the worst case
  (cache miss); one list call in the common case (cache hit). Outbound timeouts: 5s connect / 30s read
  (SOP §5), consistent with the sibling designs in this repo.
- **Security**: Credentials read only from `X-Msp360-Username`/`X-Msp360-Password` headers, never an
  env-var fallback (SOP §3.1); the vendor's `access_token` lives only inside `api_client.py`'s cache
  (keyed on the credential pair, never logged, never returned to a tool caller) and is never passed to
  or through `tools/companies.py` beyond using it as a bearer header on the one outbound call (AC6).
- **Multi-tenant isolation**: Every request carries its own tenant's MSP360 credentials in headers;
  the shared cache's key is the credential pair itself, so two tenants with different credentials
  never share a cache entry, and a request's response is built only from that request's own vendor
  call (AC5).
- **Observability**: One structured log line per call — tool name, outcome (`ok` / `unauthorized` /
  `upstream_error`), MSP360 HTTP status code, latency, result count. Never the username, password, or
  access_token (AC6, SOP §6/§11).

## Test cases

(Pass/fail statements; full steps and mock setups live in the sibling `.ac.json`.)

- **TC1** (AC1): Given a mocked vendor response with two companies, when `msp360_list_companies` is
  called, then the response has `count: 2`, two `companies` entries each with exactly
  `company_id`/`name`/`storage_limit_bytes`/`license_settings`, and `has_more: false`.
- **TC2** (AC2): Given a mocked vendor response with zero companies, when `msp360_list_companies` is
  called, then the response is `{"companies": [], "count": 0, "has_more": false}`, not an error.
- **TC3** (AC3): Given the vendor login call returns 401, when `msp360_list_companies` is called, then
  the result is `{"error": {"code": "unauthorized", "retryable": false, ...}}` and `/api/Companies` is
  never called (assert the mocked list client was never invoked).
- **TC4** (AC4): Given the request is missing `X-Msp360-Username`, when `msp360_list_companies` is
  called, then the server responds HTTP 401 listing the required headers, and no HTTP call to MSP360
  is made.
- **TC5** (AC5): Given two concurrent requests with different credentials (tenant A's vendor mock
  returns company "Acme", tenant B's returns company "Contoso"), when both are in flight at once, then
  tenant A's result contains only "Acme" and tenant B's only "Contoso".
- **TC6** (AC6): Given a mocked vendor 200 login response containing a distinctive `access_token`
  value, when `msp360_list_companies` is called and its response and all captured log output are
  searched for that exact string, then it is not found anywhere.
- **TC7** (AC7): Given a mocked vendor response with 60 companies, when `msp360_list_companies()` is
  called with no arguments, then exactly 50 are returned and `has_more: true`; when called with
  `limit=200`, then all 60 are returned and `has_more: false` (the hard cap of 200 is not the binding
  limit here); when called with `limit=500`, then at most 200 are returned (hard cap wins over the
  requested limit).
- **TC8** (AC8): Given the `/api/Companies` call times out or returns a 5xx response, when
  `msp360_list_companies` is called, then the result is `{"error": {"code": "upstream_error",
  "retryable": true, ...}}`.
