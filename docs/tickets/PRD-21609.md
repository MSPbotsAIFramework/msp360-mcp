## Requirement understanding

One line: Add an MSP360 Managed Backup connector/MCP with a msp360_list_domains tool that lists the domains/apps under an MSP360 account via GET /api/apps/domains/ (gap found in the EMD Networking Services Rewst "MSP360" flow, 29 runs/365d, evidence grade A; mspbots-gap-register.xlsx item 43).

The ticket is one of six sibling "tool" tickets (PRD-21604–21609) that migrate specific steps of an
existing Rewst automation for client EMD Networking Services into Agent-platform MCP tools. In the
original Rewst flow, `custom.generic_request` calls `GET /api/apps/domains/` with
`Authorization: Bearer {{ CTX.authentication_response.access_token }}` — the token obtained by the
login step sibling ticket PRD-21604 already designed as `msp360_provider_login`. The ticket's own
text flags a naming oddity worth resolving up front: the Rewst task that performs this call is named
`get_msp360_computers`, but its actual path is `/api/apps/domains/`, not a computers endpoint. Sources
below (vendor Swagger) confirm the path returns domain-level backup storage records, not a list of
computers, so this design treats the task's historical name as a Rewst-side misnomer and builds
exactly what the endpoint and the ticket's own wording ask for ("list the apps/domains under the
MSP360 portal," translated from the ticket's Chinese description — see Ticket thread): a
domain-listing tool, not a computer-listing tool (that is PRD-21607's `msp360_list_user_computers`,
already designed on a sibling branch — see Current state and Non-goals).

## Product design

### Goals / Non-goals

**Goals** (this ticket only):
- An Agent can list the domain-level backup storage records MSP360 tracks for the connected provider
  account — the exact vendor call the gap register names (`GET /api/apps/domains`) — so the
  Rewst-to-MSPbots mapping for this gap-register line item (item 43) stays traceable.
- The tool follows this repo's already-fixed header-credential pattern (`X-Msp360-Username` /
  `X-Msp360-Password`, identical names to every sibling design) and its token-handling pattern
  (internal login via a shared, cached `api_client.py` helper — never a token handed to the Agent).
- The returned list is capped and paginated per the platform's token-economy rule (SOP §2.5), even
  though the vendor endpoint itself has no pagination.

**Non-goals** (explicitly out of scope for this ticket):
- Listing computers, companies, backup users, or storage/license packages as standalone tools —
  PRD-21607, PRD-21605, PRD-21606, and PRD-21608 own those respectively. In particular, despite the
  Rewst task's historical name `get_msp360_computers`, this ticket does **not** build a computer
  listing tool — `GET /api/apps/domains` is a different vendor resource (CloudBackup tag) from
  `GET /api/Users/{userId}/Computers` (Computers tag, PRD-21607).
- Backup-health monitoring or plan start/stop, and the `msp360_provider_login` connectivity-check
  tool — PRD-21273 and PRD-21604 own those respectively; zero overlap.
- Any write operation against domains — the Swagger excerpt found for this ticket shows only the one
  `GET` under the CloudBackup tag; no domain create/update/delete endpoint was named by the ticket or
  found during research, so none is built.
- Per-domain detail lookup by id — the ticket and the vendor endpoint are both list-only; there is no
  `GET /api/apps/domains/{id}` in the Swagger excerpt this design read.

### Acceptance criteria

- **AC1**: Given valid MSP360 provider credentials are supplied in the connector's headers and at
  least one domain exists under that provider account, When the Agent calls `msp360_list_domains`,
  Then it receives `{"domains": [{"domain", "storage", "storage_limit": {"total_limit",
  "command_drive_limit", "other_services_limit"}, "storage_usage_total", "activated_licenses"}, ...],
  "count": N, "has_more": false}` where `count` equals the number of items in `domains`, and no item
  contains any field other than those five top-level keys.
- **AC2 (empty is not an error)**: Given valid credentials and zero domains exist under that provider
  account, When the Agent calls `msp360_list_domains`, Then it receives `{"domains": [], "count": 0,
  "has_more": false}` — not a `not_found` error (SOP §4.2's "empty is not `not_found`" rule).
- **AC3**: Given the MSP360 provider credentials are rejected by the vendor (wrong password, revoked
  API credential), When the Agent calls `msp360_list_domains`, Then it receives a structured error
  envelope with `code: "unauthorized"` and `retryable: false` — never a raw exception, stack trace, or
  HTTP 500.
- **AC4**: Given the request to the MCP server is missing one or both required credential headers,
  When the Agent calls `msp360_list_domains`, Then the server returns HTTP 401 with a body listing
  which header(s) are required, and does not attempt a call to MSP360 at all.
- **AC5 (multi-tenant)**: Given two different MSPbots tenants call `msp360_list_domains` concurrently
  with two different sets of credentials (each provider account having a different domain list), When
  both requests are in flight at the same time, Then each tenant's response contains only that
  tenant's own domains — no domain, credential, or cached token is ever attributable to another
  tenant's request.
- **AC6 (security)**: Given any outcome of `msp360_list_domains` (success, rejected credentials, or an
  upstream error), When the tool returns its result or the server writes a log line for the call, Then
  neither the submitted password nor the vendor's `access_token` ever appears in the tool's response
  body or in any log output.
- **AC7 (pagination)**: Given a provider account with more domains than the tool's default `limit`,
  When the Agent calls `msp360_list_domains` with no `limit` argument, Then at most 50 domains are
  returned and `has_more: true` is set; When the Agent calls it with `limit` set above the hard cap of
  200, Then at most 200 are returned (the hard cap wins); When the serialized result would exceed
  20,000 characters before either limit is hit, Then the result is truncated at whichever bound is hit
  first and `has_more: true` is set (SOP §2.5's "character cap wins" rule).
- **AC8 (resilience)**: Given MSP360's `/api/apps/domains` endpoint is unreachable, times out, or
  returns a 5xx response, When the Agent calls `msp360_list_domains`, Then it receives a structured
  error with `code: "upstream_error"` and `retryable: true`, not an unhandled exception.

### Open questions

- **[non-blocking, resolved by vendor schema] OQ1**: The ticket's Rewst task is historically named
  `get_msp360_computers` even though its path and field shape (`Domain`, `Storage`, `StorageLimit`,
  `StorageUsage`, `ActivatedLicenses`) are about domain-level backup storage, not computers.
  **Resolution, not an assumption**: the live vendor Swagger independently confirms `/api/apps/domains`
  is tagged `CloudBackup` and is a distinct resource from `Computers` (PRD-21607's tag); this design
  builds the domain-listing tool the endpoint and the ticket's own body text describe, and treats the
  Rewst task name as a historical misnomer on Rewst's side, not a spec for this ticket. If this
  judgment is wrong — i.e., the reporter actually wanted computer data under a misleadingly-named
  endpoint — that would be a different ticket's scope (PRD-21607 already covers computers); flagged
  here so a reviewer can object before dev starts.
- **[non-blocking, assumption] OQ2**: The ticket's path has a trailing slash
  (`/api/apps/domains/`); the Swagger renders it without one. **Assumption**: these are the same
  endpoint and the Swagger's machine-readable form is authoritative; `api_client.py` calls the
  no-trailing-slash form. If the vendor's gateway actually requires the trailing slash, only
  `api_client.py`'s URL string changes.
- **[non-blocking, assumption] OQ3**: Neither the ticket nor the Swagger excerpt states units for
  `Storage`/`StorageLimit`/`StorageUsage.Total` (bytes vs. GB vs. a formatted string — `Storage` is
  typed as a string in the Swagger, unlike `StorageUsage.Total` which is numeric). **Assumption**: pass
  these fields through using the vendor's own types verbatim (string for `storage`, numeric for the
  `storage_limit`/`storage_usage_total` fields) rather than guessing a unit conversion; if MSP360
  documents the unit later, a labeled/converted field can be added additively (SOP §13) without
  breaking the existing fields.
- **[non-blocking, not this ticket's call to make] OQ4**: This design reuses `dev/PRD-21273`'s
  token-cache `api_client.py` shape (see Tech design · Option analysis) rather than building a second,
  independent login/cache implementation. If, by the time this ticket's dev leg runs, none of
  PRD-21273/21604/21605/21606 has landed in `main` yet, this ticket's dev leg becomes a first mover and
  should build the token-cache shape itself (consistent with what every sibling design already
  anticipates via the repo's `dev-lock`) rather than inventing a different one.

## Tech design

### Conclusion

Add one new tool, `msp360_list_domains`, to the `msp360-mcp` service skeleton (Python 3.12 + uv +
FastMCP, per the vendor-mcp-development SOP's reference layout) — building the skeleton if none of
the sibling tickets' dev work has landed yet, or extending it (adding one function to `api_client.py`
and one new `tools/domains.py`) if it has. The tool takes optional `limit`/`offset`, calls `GET
https://api.mspbackups.com/api/apps/domains` using a bearer token obtained (and cached) via the same
login helper PRD-21273's/PRD-21605's/PRD-21606's tools use, and maps the result to a trimmed,
paginated JSON object or a structured error.

### Data & API contract

**Header credentials** (identical to every sibling design — same repo, same connector, must not
diverge):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Msp360-Username` | Yes | MSP360 Managed Backup provider-account username | MSP360 admin portal → Settings → API credentials |
| `X-Msp360-Password` | Yes | MSP360 Managed Backup provider-account password | Same as above |

**Vendor calls** (inside `api_client.py`):

```
POST https://api.mspbackups.com/api/Provider/Login     (via the shared, cached login() helper)
  body: {"UserName": "<from header>", "Password": "<from header>"}
  200 -> {"access_token": "...", "expires_in": <seconds>}
  401/403 -> credentials rejected

GET  https://api.mspbackups.com/api/apps/domains        (Authorization: Bearer <token>)
  200 -> [ {"Domain": "...", "Storage": "...",
            "StorageLimit": {"TotalLimit": <num>, "CommandDriveLimit": <num>, "OtherServicesLimit": <num>},
            "StorageUsage": {"Total": <num>}, "ActivatedLicenses": <int>} ]
  401/403 -> token rejected (one reactive retry with a refreshed token, then unauthorized — same
             retry policy every sibling's api_client.py already specifies)
  5xx / timeout -> upstream error
```

**Tool contract** (Agent-facing, returned as a compact JSON string per SOP §4.1):

```
msp360_list_domains(limit?: int = 50, offset?: int = 0)
  -> {"domains": [{"domain", "storage", "storage_limit": {"total_limit", "command_drive_limit",
      "other_services_limit"}, "storage_usage_total", "activated_licenses"}],
      "count": N, "has_more": bool}
```

All five vendor fields are kept (nothing to trim — `DomainModel` has no extra fields beyond what the
ticket asks for), renamed to snake_case: `Domain`→`domain`, `Storage`→`storage`,
`StorageLimit.TotalLimit/CommandDriveLimit/OtherServicesLimit`→
`storage_limit.total_limit/command_drive_limit/other_services_limit`, `StorageUsage.Total`→
`storage_usage_total`, `ActivatedLicenses`→`activated_licenses`. `limit` default 50 / hard cap 200
(SOP §2.5); since the vendor endpoint has no server-side pagination, the connector fetches the full
vendor list once and applies `limit`/`offset` client-side; if the trimmed, paginated result would
still exceed 20,000 characters, truncate further and set `has_more=true` (character cap wins, AC7).

**Error envelope** (SOP §4.2):

| Vendor / server condition | `code` | `retryable` |
|---|---|---|
| Missing `X-Msp360-Username` and/or `X-Msp360-Password` header | *(HTTP 401 from middleware, before any tool-level envelope — AC4)* | n/a |
| Login call (`/api/Provider/Login`) returns 401/403 | `unauthorized` | false |
| `/api/apps/domains` returns 401/403 after one retry-with-refreshed-token | `unauthorized` | false |
| Vendor returns 400/422 (defensive mapping — not expected, this endpoint takes no input) | `invalid_argument` | false |
| Vendor returns 429 | `rate_limited` | true |
| Vendor returns 5xx, or connect/read timeout | `upstream_error` | true |
| Anything else unexpected | `upstream_error` | true |

Zero domains is a normal successful result (AC2), never `not_found` — `not_found` is reserved for
"fetch a specific resource by id that doesn't exist," which this list-only tool never does.

**Backward compatibility**: N/A — brand-new tool. Tool name uses the `msp360_` prefix so it cannot
collide with any other vendor's tools in the same Agent session, or with this repo's other tools
(`msp360_provider_login`, PRD-21273's six, `msp360_list_companies`, `msp360_list_users`, and the
remaining gap-register tool `msp360_list_user_computers`/`msp360_list_packages`).

### Key flow / sequence

```
Agent -> Gateway -> msp360-mcp: msp360_list_domains(limit?, offset?)
  msp360-mcp: read X-Msp360-Username / X-Msp360-Password from the request (middleware);
              missing either -> 401, do not call the vendor (AC4)
  msp360-mcp -> api_client.login(): cached token for (username, password), or a fresh
                POST /api/Provider/Login if absent/expired
  msp360-mcp -> MSP360 API: GET /api/apps/domains  (Authorization: Bearer <token>)
  MSP360 API -> msp360-mcp: 200 [DomainModel, ...]  |  401/403  |  5xx/timeout
  msp360-mcp: rename fields to snake_case (domain/storage/storage_limit/storage_usage_total/
              activated_licenses); apply limit/offset and the 20,000-character cap (whichever binds
              first); discard the raw access_token from memory once the call completes
  msp360-mcp -> Agent: {"domains": [...], "count": N, "has_more": bool}
                      | structured error envelope (unauthorized | upstream_error | ...)
```

### Non-functional

- **Idempotency & concurrency**: Read-only, naturally idempotent — repeated calls with the same
  `limit`/`offset` return the same domains (modulo upstream changes). The shared token cache is keyed
  per `(username, password)`, not per tenant id, but since each tenant supplies its own distinct
  credential pair, this is equivalent to per-tenant isolation in practice (AC5) — the same isolation
  argument every sibling design already makes for its own tools sharing the same cache.
- **Performance**: One cached-or-fresh login call plus one list call per invocation in the worst case
  (cache miss); one list call in the common case (cache hit). Outbound timeouts: 5s connect / 30s read
  (SOP §5), consistent with every sibling design in this repo.
- **Security**: Credentials read only from `X-Msp360-Username`/`X-Msp360-Password` headers, never an
  env-var fallback (SOP §3.1); the vendor's `access_token` lives only inside `api_client.py`'s cache
  (keyed on the credential pair, never logged, never returned to a tool caller) and is never passed to
  or through `tools/domains.py` beyond using it as a bearer header on the one outbound call (AC6).
- **Multi-tenant isolation**: Every request carries its own tenant's MSP360 credentials in headers;
  the shared cache's key is the credential pair itself, so two tenants with different credentials
  never share a cache entry, and a request's response is built only from that request's own vendor
  call (AC5).
- **Observability**: One structured log line per call — tool name, outcome (`ok` / `unauthorized` /
  `upstream_error`), MSP360 HTTP status code, latency, result count. Never the username, password, or
  access_token (AC6, SOP §6/§11).
