## Requirement understanding

One line: Add a msp360_list_user_computers tool to the MSP360 Managed Backup MCP connector that lists the computers under a given backup user together with each computer's backup status, last backup date, and plans — the data source for a backup-audit report — replacing the custom Rewst integration EMD Networking Services uses today.

Sources: ticket `text_content` (PRD-21607, item 41 of `mspbots-gap-register.xlsx`, evidence grade A,
verified 2026-10-28) + prior `[BLOCKED · vendor-mcp]` comment on this same ticket (2026-11-02, same
machine, superseded once the repo existed) for the original ask wording; vendor API confirmed by
fetching the live Swagger spec and the vendor's help-site method pages (2026-11-03, see Current state);
wiki checked and found not to cover this connector (see below).

The ticket is one of seven sibling "tool"/"connector" tickets (PRD-21273, PRD-21604–21609) that migrate
an existing Rewst automation for client EMD Networking Services into Agent-platform MCP tools. In the
original Rewst flow, `custom.generic_request` loops over the users returned by the sibling
`msp360_list_users` tool (PRD-21606) and calls `GET /api/Users/{userId}/Computers` for each one, to
build a per-user list of computers for a backup-audit report. This ticket is that next step: give the
Agent a tool that, given one `user_id` (sourced from `msp360_list_users`' output), returns that user's
computers and their backup status.

## Product design

### Goals / Non-goals

**Goals** (this ticket only):
- An Agent that already has a `user_id` (from `msp360_list_users`, PRD-21606) can, in one tool call,
  get every computer under that backup user, each with its current backup status, most recent backup
  date, and the plans contributing to that status — enough to answer "which computers for this user are
  not backing up correctly" without a second drill-down call, which is what the audit-report use case
  the ticket names needs.
- The tool follows this repo's fixed conventions: `X-Msp360-Username`/`X-Msp360-Password` headers, the
  cached-login `api_client.py` shape, the `msp360_` tool-name prefix, and SOP §2.5 response trimming /
  pagination.

**Non-goals** (explicitly out of scope for this ticket):
- Listing backup users or companies — PRD-21606/PRD-21605 own those; this tool takes `user_id` as an
  input, it does not discover it.
- Fleet-wide (all users) monitoring, or plan start/stop/history — PRD-21273 owns
  `msp360_get_monitoring`, `msp360_list_plans`, `msp360_get_plan_info`, `msp360_get_plan_history`,
  `msp360_start_plan`, `msp360_stop_plan`. This tool's `plans` array is a status *summary* per plan
  (id, name, status, last start, error message) for the computers of one user — not a replacement for
  PRD-21273's history/control tools, and it does not expose `hid` (PRD-21273's plan-tool identifier;
  this ticket's vendor calls never receive or need it).
- Deleting a user's computers — the vendor API also exposes `DELETE /api/Users/{userId}/Computers`
  (confirmed in the same Swagger spec), but the ticket only asks to *list*; not built here.
- Packages or domains — PRD-21608/21609 own those; unrelated resources.
- A new status-taxonomy endpoint or admin surface for the `no_data` state this design introduces (see
  Tech design) — it is a response value, not a new capability.

### Acceptance criteria

- **AC1 (happy path / shape)**: Given valid MSP360 credentials and a `user_id` with at least one
  computer that has at least one monitored plan, When the Agent calls
  `msp360_list_user_computers(user_id)`, Then it receives
  `{"computers": [{"destination_id", "computer_name", "status", "last_backup_date", "plans": [...]}],
  "count": N, "has_more": bool}` where `count` equals the number of items in `computers`, and each
  `plans` entry has exactly `plan_id`, `plan_name`, `status`, `last_start`, `error_message`.
- **AC2 (empty is not an error)**: Given valid credentials and a `user_id` with zero computers, When the
  Agent calls the tool, Then it receives `{"computers": [], "count": 0, "has_more": false}` — not a
  `not_found` error (SOP §4.2's "empty is not `not_found`" rule, same as every sibling tool).
- **AC3 (computer with no backup data yet)**: Given a computer is returned by the vendor's computer
  inventory for that user but has no matching record in the vendor's monitoring data (e.g. a newly
  added endpoint that has not run a backup yet), When the tool is called, Then that computer's entry has
  `status: "no_data"`, `last_backup_date: null`, and `plans: []` — it is still listed (not dropped),
  because the ticket's purpose is an audit report that must show "never backed up" computers too.
- **AC4 (status aggregation across multiple plans)**: Given a computer has more than one monitored plan
  with different statuses (e.g. one `Success`, one `Error`), When the tool is called, Then the
  computer's top-level `status` is the most severe one present (see Tech design's priority order) and
  `last_backup_date` is the latest `LastStart` among that computer's plans.
- **AC5 (status labels, not raw codes)**: Given the vendor returns a numeric `Status` code (0–7) for a
  plan, When the tool builds its response, Then it reports the documented label
  (`success`/`overdue`/`error`/`running`/`unknown`/`interrupted`/`unexpectedly_closed`/`warning`), never
  the raw integer.
- **AC6 (auth failure)**: Given the MSP360 credentials are rejected by the vendor, When the Agent calls
  the tool, Then it receives a structured error with `code: "unauthorized"`, `retryable: false` — never
  a raw exception or HTTP 500.
- **AC7 (missing headers)**: Given the request to the MCP server is missing one or both required
  credential headers, When the tool is called, Then the server returns HTTP 401 listing the required
  header(s), and makes no call to MSP360 at all.
- **AC8 (multi-tenant)**: Given two different MSPbots tenants call the tool concurrently with two
  different credential pairs (each with a distinct computer/user list), When both requests are in
  flight at the same time, Then each tenant's response contains only that tenant's own data — no
  computer, credential, or cached token is ever attributable to another tenant's request.
- **AC9 (security)**: Given any outcome of the tool (success, rejected credentials, or an upstream
  error), When the tool returns its result or the server writes a log line, Then neither the submitted
  password nor the vendor's `access_token` ever appears in the response body or any log output.
- **AC10 (pagination)**: Given a `user_id` with more computers than the tool's default `limit`, When
  the Agent calls the tool with no `limit` argument, Then at most 50 computers are returned and
  `has_more: true`; When `limit` is set above the hard cap of 200, Then at most 200 are returned (the
  hard cap wins); When the serialized result would exceed 20,000 characters before either limit is hit,
  Then it is truncated at whichever bound is hit first and `has_more: true` is set (SOP §2.5's
  "character cap wins" rule).
- **AC11 (resilience)**: Given either vendor call (the computer-inventory call or the monitoring call)
  is unreachable, times out, or returns a 5xx response, When the Agent calls the tool, Then it receives
  a structured error with `code: "upstream_error"`, `retryable: true` — not an unhandled exception;
  given either call returns 429, the error is `code: "rate_limited"`, `retryable: true`.
- **AC12 (unrecognized user_id)**: Given the `user_id` argument does not correspond to any backup user
  the connected account manages, When the Agent calls the tool, Then it receives a structured error
  (`invalid_argument` for a 400/422 vendor response, `not_found` for a 404) rather than a raw exception
  or a silently empty success — distinct from AC2 (AC2 is a *valid* user with zero computers; AC12 is an
  *invalid* user id). See OQ2: the vendor's actual behavior for this case is not documented and must be
  confirmed before merge.

### Open questions

- **[non-blocking, this design's own convention] OQ1**: The vendor documents per-*plan* status
  (`MonitoringPlanStatus`), not a per-*computer* status — grouping multiple plans on one computer down
  to a single top-level `status` is this design's own choice, not a vendor rule. **Decision**: most
  severe wins, in the fixed order `error > unexpectedly_closed > interrupted > warning > overdue >
  running > unknown > success > no_data` (worst-first, so a single failing plan on an otherwise-healthy
  computer is never hidden behind a passing one — the audit-report use case this ticket names is
  specifically about catching failures). If a different precedence is wanted, only this ordering table
  changes, not the tool's contract shape (`status` is still one string per computer).
- **[non-blocking, assumption] OQ2**: Neither the Swagger spec nor the help-site page for
  `GET /api/Users/{userid}/Computers` documents what the vendor returns for a `user_id` that does not
  exist (no 400/404 response is listed — only the 200 array is documented, see Current state).
  **Assumption**: a non-2xx response is mapped through the standard error table (400/422 →
  `invalid_argument`, 404 → `not_found`, per AC12); if the vendor instead silently returns 200 with an
  empty array for an unrecognized `user_id` (making it indistinguishable from AC2's "valid user, zero
  computers" case), that is accepted as the vendor's actual contract and AC12 does not apply — dev
  should confirm against a live account or by testing a clearly-invalid id against the Swagger
  "Try it out" console before merge, and record which behavior was observed in Self-test.
- **[non-blocking, cross-ticket note, not this ticket's call to make] OQ3**: This tool's per-user,
  per-computer status view and PRD-21273's `msp360_get_monitoring(user_id=...)` both read
  `GET /api/Monitoring/{userId}` for the same user and both can answer "is this user's backup healthy."
  They are not duplicates — `msp360_get_monitoring` returns a flat list of plan-run records (built for
  fleet-wide monitoring across companies/computers/users), while `msp360_list_user_computers` returns
  one row per computer (built around this ticket's own computer-inventory call, for the audit-report use
  case the gap register names, and keyed off `msp360_list_users`' `user_id` output specifically). Each
  tool calls the vendor independently; there is no shared code, contract, or ordering dependency between
  them. Flagged for awareness only, the same way PRD-21273's own OQ3 flagged its relationship to
  PRD-21604.
- **[non-blocking, assumption] OQ4**: This design reuses `dev/PRD-21273`'s/`dev/PRD-21605`'s/
  `dev/PRD-21606`'s cached-login `api_client.py` shape rather than building a new one. If none of the
  four sibling branches has landed in `main` by the time this ticket's dev leg runs, that dev leg
  becomes the first mover and should build the cached-login shape itself (the same contingency every
  later-landing MSP360 sibling design has already anticipated via the repo's `dev-lock`).

TL;DR: `msp360-mcp` now has four unmerged sibling designs on the same empty scaffold. This ticket's own
named endpoint (`GET /api/Users/{userId}/Computers`) only returns a computer's name and policy id, not
the backup-status fields the ticket also asks for — those live on a second, already-public vendor
endpoint (`GET /api/Monitoring/{userId}`, the same one PRD-21273 uses for its own fleet-wide tool). This
design calls both (exactly two vendor calls, not one per computer), joins them by `ComputerName`, maps
the vendor's now-fully-documented plan-status enum to labels, and aggregates per-plan status to one
value per computer by a documented "most severe wins" rule that is this design's own convention, not a
vendor rule.

## Tech design

### Conclusion

Add one new tool, `msp360_list_user_computers`, to the `msp360-mcp` service skeleton (Python 3.12 + uv
+ FastMCP, per the vendor-mcp-development SOP's reference layout) — building the skeleton if none of
the four sibling tickets' dev work has landed yet, or extending it if it has. The tool takes a required
`user_id` and optional `limit`/`offset`, makes two vendor calls behind the shared cached-login helper
(`GET /api/Users/{userid}/Computers` for the inventory, `GET /api/Monitoring/{userId}` for status), and
returns a trimmed, joined, paginated JSON object or a structured error.

### Where the current implementation lives

Nothing merged — `path:line` for "the whole repo" is `README.md:1-2`, a two-line placeholder
(`prepare_repo.py` output, HEAD `c4c9439`). `dev/PRD-21273`, `dev/PRD-21604`, `dev/PRD-21605`, and
`dev/PRD-21606` are the only other MSP360 work products that exist anywhere in MSPbotsAIFramework at

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Return only what `GET /api/Users/{userId}/Computers` documents (`destination_id`, `computer_name`) and drop status/last-backup-date/plans entirely | Single vendor call, zero merge logic | Simplest possible implementation; exactly matches the one endpoint the ticket names by path | Fails the ticket's own stated purpose — "and their backup status" (the ticket's own description names this the data source for a backup-audit report) is the reason the tool exists; shipping only a name list would make every one of the ticket's three other named fields silently disappear, discovered only when an Agent/Rewst-migration consumer tries to use them | Rejected |
| B. For every computer returned by the inventory call, fetch its plans individually (`GET /api/Computers/{hid}/Plans` + `/Plans/{id}/info`, PRD-21273's per-computer endpoints) | Would give live, authoritative per-plan detail | Most "live" data, reuses PRD-21273's documented endpoints | N+1 vendor calls (one round-trip per computer, per invocation) — a user with 50 computers means 50+ extra HTTP calls per tool call, with proportional latency and rate-limit exposure (SOP §5's connection-reuse rule doesn't fix call *count*); worse, those endpoints key on `hid` (a different vendor identifier used by PRD-21273's Plans/Computers family), which `GET /api/Users/{userId}/Computers` does not return — there is no field in the inventory response this design could use to call them without a third vendor round-trip per computer just to resolve `ComputerName` → `hid` | Rejected |
| C. Call `GET /api/Monitoring/{userId}` once (same `userId` already in hand) alongside the inventory call, and group its per-plan records by `ComputerName` to attach status/plans/last-backup-date to each inventory row | Exactly 2 vendor calls total regardless of computer or plan count; `ComputerName` is the field both responses share, so no extra lookup call is needed; delivers every field the ticket names | Status is aggregated per-computer by this design's own rule (OQ1), not a vendor-native field; depends on `ComputerName` strings matching exactly between the two endpoints (reasonable — both come from the same backend — but unconfirmed against a live account, noted in Risks) | **Chosen** |

**Vendor calls** (inside `api_client.py`):

```
POST https://api.mspbackups.com/api/Provider/Login     (via the shared, cached login() helper)
  body: {"UserName": "<from header>", "Password": "<from header>"}
  200 -> {"access_token": "...", "expires_in": <seconds>}
  401/403 -> credentials rejected

GET  https://api.mspbackups.com/api/Users/{userid}/Computers      (Authorization: Bearer <token>)
  200 -> [ {"DestinationId": "<guid>", "ComputerName": "<string>"} ]
  (vendor behavior for an unrecognized userid is undocumented — OQ2)

GET  https://api.mspbackups.com/api/Monitoring/{userId}            (Authorization: Bearer <token>)
  200 -> [ {"ComputerName": "...", "PlanId": "...", "PlanName": "...", "Status": <int 0-7>,
            "LastStart": "<date-time>", "NextStart": "<date-time>", "ErrorMessage": "...", ...} ]
  401/403 -> token rejected (one reactive retry with a refreshed token, then unauthorized)
  5xx / timeout -> upstream error
```

`MonitoringPlanStatus` enum (confirmed, see Current state): `0 Success, 1 Overdue, 2 Error, 3 Running,
4 Unknown, 5 Interrupted, 6 UnexpectedlyClosed, 7 Warning` → lowercase-with-underscores labels
(`success`, `overdue`, `error`, `running`, `unknown`, `interrupted`, `unexpectedly_closed`, `warning`).

**Tool contract** (Agent-facing, returned as a compact JSON string per SOP §4.1):

```
msp360_list_user_computers(user_id: str, limit?: int = 50, offset?: int = 0)
  -> {"computers": [{
        "destination_id": "<guid>",
        "computer_name": "<string>",
        "status": "success|overdue|error|running|unknown|interrupted|unexpectedly_closed|warning|no_data",
        "last_backup_date": "<ISO 8601 timestamp>" | null,
        "plans": [{"plan_id", "plan_name", "status", "last_start", "error_message"}]
      }],
      "count": N, "has_more": bool}
```

Join/aggregation algorithm: group the Monitoring response by `ComputerName`; for each computer returned
by the inventory call, attach the matching group (if any) as `plans` (each record mapped to
`plan_id`/`plan_name`/`status` (labeled)/`last_start`/`error_message`); `status` = the most severe label
present using the fixed order `error > unexpectedly_closed > interrupted > warning > overdue > running >
unknown > success` (OQ1); `last_backup_date` = the latest `LastStart` among that computer's plans. A
computer with no matching group gets `status: "no_data"`, `last_backup_date: null`, `plans: []` (AC3).
`limit` default 50 / hard cap 200 (SOP §2.5) applied to the `computers` list (not separately to nested
`plans`, which are naturally small per computer); if the serialized, joined, paginated result would
still exceed 20,000 characters, truncate the `computers` list further and set `has_more=true` (character
cap wins, AC10).

**Error envelope** (SOP §4.2, consistent with every sibling tool in this repo):

| Vendor / server condition | `code` | `retryable` |
|---|---|---|
| Missing `X-Msp360-Username` and/or `X-Msp360-Password` header | *(HTTP 401 from middleware, before any tool-level envelope — AC7)* | n/a |
| Login call (`/api/Provider/Login`) returns 401/403 | `unauthorized` | false |
| Either vendor call returns 401/403 after one retry-with-refreshed-token | `unauthorized` | false |
| Either vendor call returns 400/422 (incl. an unrecognized `user_id`, per OQ2's assumption) | `invalid_argument` | false |
| Either vendor call returns 404 (incl. an unrecognized `user_id`, per OQ2's assumption) | `not_found` | false |
| Either vendor call returns 429 | `rate_limited` | true |
| Either vendor call returns 5xx, or connect/read timeout | `upstream_error` | true |
| Anything else unexpected | `upstream_error` | true |

Zero computers for a *valid* user is a normal successful result (AC2) — `not_found` is reserved for "the
given `user_id` itself does not exist" (AC12), a different case from "this user exists and has no
computers."

**Backward compatibility**: N/A — brand-new tool. The `msp360_` prefix prevents collisions with this
repo's other tools (`msp360_provider_login`, `msp360_list_companies`, `msp360_list_users`, PRD-21273's
six) or any other vendor's tools in the same Agent session.

### Key flow / sequence

```
Agent -> Gateway -> msp360-mcp: msp360_list_user_computers(user_id="U1")
  msp360-mcp: read X-Msp360-Username / X-Msp360-Password from the request (middleware);
              missing either -> 401, do not call the vendor (AC7)
  msp360-mcp -> api_client.login(): cached token for (username, password), or a fresh
                POST /api/Provider/Login if absent/expired
  msp360-mcp -> MSP360 API: GET /api/Users/U1/Computers   (Authorization: Bearer <token>)
  MSP360 API -> msp360-mcp: 200 [ {DestinationId, ComputerName}, ... ]
  msp360-mcp -> MSP360 API: GET /api/Monitoring/U1         (Authorization: Bearer <token>)
  MSP360 API -> msp360-mcp: 200 [ {ComputerName, PlanId, PlanName, Status, LastStart, ...}, ... ]
  msp360-mcp: group monitoring records by ComputerName; join onto each inventory row;
              map Status codes to labels; aggregate per-computer status (OQ1);
              apply limit/offset and the 20,000-character cap (whichever binds first)
  msp360-mcp -> Agent: {"computers": [...], "count", "has_more"}
                      | structured error envelope (unauthorized | upstream_error | ...)
```

### Non-functional

- **Idempotency & concurrency**: Read-only, naturally idempotent — repeated calls with the same
  `user_id`/`limit`/`offset` return the same data (modulo upstream changes). No local state beyond the
  in-memory token cache (keyed by credential fingerprint).
- **Performance**: Exactly two vendor calls per invocation (plus a cached-or-fresh login), regardless of
  how many computers or plans the user has — the chosen option (C) was picked specifically to avoid the
  N+1 pattern option B would have introduced. Outbound timeouts: 5s connect / 30s read (SOP §5),
  consistent with every sibling design in this repo.
- **Security**: Credentials read only from `X-Msp360-Username`/`X-Msp360-Password` headers, never an
  env-var fallback; the vendor's `access_token` lives only inside `api_client.py`'s cache (never logged,
  never returned to a tool caller) and is used only as a bearer header on the two outbound calls (AC9).
- **Multi-tenant isolation**: Every request carries its own tenant's MSP360 credentials in headers; the
  shared cache's key is the credential pair itself, so two tenants with different credentials never
  share a cache entry or a vendor response (AC8).
- **Observability**: One structured log line per call — tool name, `user_id` (not credentials), MSP360
  HTTP status codes for both calls, latency, result count. Never the username, password, or
  access_token.
