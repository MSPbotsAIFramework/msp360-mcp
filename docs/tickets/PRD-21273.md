# PRD-21273 · [Backup & BCDR] MSP360

## Requirement understanding

One line: Monitor backup health across companies and computers, and start or stop backup plan runs, via MSP360.

MSP360 (formerly CloudBerry) is a backup/BCDR product used by MSPs. The reporter wants the Agent
platform to be able to (a) see whether scheduled backups are healthy — which plans ran, when, and
whether they succeeded, across every company and computer the provider manages — and (b) trigger or
cancel a specific backup plan's run on demand. The ticket links
https://conduit.wyre.ai/plugins/msp360, a third-party "Conduit" catalog page that describes the same
two capabilities in one sentence; it is not vendor API documentation and is treated only as a
restatement of the ask (see Sources below), not as a source of technical facts.

## Product design

### Goals / Non-goals

**Goals** (this ticket only):
- An Agent can ask "is MSP360 backup healthy for <company/computer>?" and get, in one or two tool
  calls, the latest run status, errors, and data-volume figures for every plan across every company
  and computer the connected MSP360 account manages.
- An Agent can list the backup/restore plans configured on a specific computer, inspect one plan's
  current status and recent run history, and start or stop a run of that plan.
- The connector follows the same connect-once / Header-credential pattern as every other MSPbots
  connector (wiki: `ProductDocs/15-Capabilities.md` § "Connection forms") — no custom UI.

**Non-goals** (explicitly out of scope for PRD-21273, left to sibling tickets or future work):
- Listing companies, backup users, or user-computers as standalone tools — PRD-21605/21606/21607
  own that.
- Storage/license package management — PRD-21608 owns `msp360_list_packages`; unrelated resource.
- Domain/app listing — PRD-21609.
- Creating, editing, or deleting plan definitions (`POST/PUT/DELETE API/Packages`) — not asked for;
  the ticket only asks to *monitor* and *start/stop runs*, not to author plans.
- License, destination, billing, administrator, and build-related endpoints documented on
  help.mspbackups.com — none of them are part of "monitor backup health" or "start/stop a run".

### Acceptance criteria

- **AC1**: Given valid MSP360 credentials are connected, When the Agent asks for fleet-wide backup
  health, Then it receives a list of the latest run per plan across all companies and computers,
  each entry showing company, computer, plan name, last run time, status (e.g. success/error/running),
  and (when the status is an error) the error message.
- **AC2**: Given the same request, When the Agent wants to narrow the result to one backup user
  (MSP360's grouping of computers), Then it can filter by that user's id without a separate tool call.
- **AC3**: Given a computer's HID is known (e.g. from a sibling tool's output, or from an earlier
  monitoring call), When the Agent asks what backup/restore plans exist on that computer, Then it
  receives each plan's id, name, and type.
- **AC4**: Given a computer HID and a plan id, When the Agent asks for that plan's current status,
  Then it receives the plan's last/next run time, current state (idle/running/etc.), and the most
  recent error if any.
- **AC5**: Given a computer HID and a plan id, When the Agent asks for that plan's run history
  (optionally filtered to a year/month/day), Then it receives a list of past runs with start time,
  duration, status, and data volume.
- **AC6**: Given a computer HID and a plan id that is not currently running, When the Agent starts
  the plan, Then MSP360 begins a run and the tool reports the run as started (not necessarily
  completed — this is fire-and-forget against an async backup engine).
- **AC7**: Given a computer HID and a plan id that is currently running, When the Agent stops the
  plan, Then MSP360 cancels the in-progress run and the tool reports the run as stopped.
- **AC8**: Given an invalid or already-stopped plan is targeted for stop (or an invalid plan/hid for
  any of the above), When the tool call is made, Then it returns a structured `not_found` /
  `invalid_argument` error rather than a raw exception or a silent no-op.
- **AC9**: Given the connected MSP360 account's credentials are wrong or expired, When any tool is
  called, Then it returns a structured `unauthorized` error — the tool never retries indefinitely nor
  silently returns stale/cached data.
- **AC10 (multi-tenant)**: Given two different MSPbots tenants each connect their own MSP360 account,
  When tenant A calls any of these tools, Then only tenant A's MSP360 data is ever returned — the
  server must not reuse tenant B's cached token or data for tenant A's request, even under concurrent
  load (this is a platform-wide MCP contract, not special to MSP360, but it is the AC the multi-tenant
  test case in §6 Test cases exists to pin down).
- **AC11**: Given a fleet with many plans, When the fleet-wide monitoring tool is called without a
  narrower filter, Then the response is capped (not an unbounded dump of every record) and says so
  when truncated.

### Open questions

- **[non-blocking] OQ1**: The exact REST paths for `.../Plans/{id}/info`, `.../Plans/{id}/history`,
  `.../Plans/{id}/start`, and `.../Plans/{id}/stop` are corroborated by a third-party reference
  implementation (see Current state) rather than directly readable vendor text (the doc site isn't
  fully crawlable from here). **Assumption**: these four sub-resources exist under
  `/api/Computers/{hid}/Plans/{id}/...` exactly as that reference implementation calls them. If
  assumption fails, only `api_client.py`'s internal path strings change — the tool names, parameters,
  and contracts in this design are unaffected. Dev should confirm against a live MSP360 test account
  (or by opening help.mspbackups.com directly in a browser, which this design pass could not do)
  before merging, and record the confirmed paths in the Self-test section.
- **[non-blocking] OQ2**: `GET /api/Monitoring`'s exact filter/pagination parameters (if any)
  are not confirmed from primary vendor text. **Assumption**: it returns the full unfiltered dataset
  and this server performs its own `limit`/`has_more` truncation client-side (§2.5 of the
  vendor-mcp-development SOP already requires this regardless of what the vendor does). If MSP360
  turns out to support server-side paging, dev may pass it through as an optimization without
  changing the tool's external contract.
- **[non-blocking] OQ3**: PRD-21604's description frames `msp360_provider_login` as
  something Rewst's workflow called explicitly before every batch of requests — that was Rewst's own
  orchestration, not necessarily meant as a pattern for this MCP server. This design does **not**
  expose a login tool to the Agent; instead, following the vendor-mcp-development SOP's Header-only
  credential model (and the existing connect-dialog UX in `ProductDocs/15-Capabilities.md`), this
  server performs the `UserName`/`Password` → bearer-token exchange internally on every request,
  using credentials from `X-Msp360-Username` / `X-Msp360-Password` headers, exactly as every other
  MSPbots connector does. If PRD-21604 is designed independently and lands on a different model
  (e.g., an explicit login tool that hands the Agent a token to pass around on later calls), that
  would conflict with this ticket's tools reading credentials straight from the connect-dialog
  headers. **This is a cross-ticket integration risk, not a blocker** — flagged again in §11 Risks —
  because this ticket's tools can be built, tested, and deployed independently of whatever PRD-21604
  decides; reconciliation (if needed) happens at whichever ticket lands second, via the shared
  `dev-lock` on this repo.

## Tech design

### Conclusion

Build six new MCP tools in the still-empty `msp360-mcp` repo, following the Python 3.12 + uv +
FastMCP reference layout from the vendor-mcp-development SOP: a `tools/plans.py` (list/info/history/
start/stop) and a `tools/monitoring.py` (fleet health), sharing one `api_client.py` that does the
`UserName`/`Password` → bearer-token exchange per request (cached per credential fingerprint, with
expiry tracked from the vendor's own `expires_in` and a single retry-on-401 as a backstop). No UI
work — the platform's generic connector dialog and detail view already do that. This is the cheapest
correct design because the two asked-for capabilities (monitor health, control runs) map directly
onto six already-documented-or-corroborated REST calls with no new data model, no migration, and no
multi-step business process to invent — the main engineering cost is getting the per-tenant,
stateless HTTP contract from §1/§3 of the SOP right, which is identical work this repo's five sibling
tickets must also do.

### Where the current implementation lives

Nothing — `path:line` for "the whole repo" is `README.md:1-2`, a two-line placeholder
(`prepare_repo.py` output, HEAD `c4c9439`). There is no prior MSP360 code in any MSPbotsAIFramework
repo to extend.

### Data & API contract

**Header credentials** (SOP §3.1 table, goes in README):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Msp360-Username` | Yes | MSP360 Managed Backup provider-account username | MSP360 admin portal → Settings → API credentials |
| `X-Msp360-Password` | Yes | MSP360 Managed Backup provider-account password | Same as above |

No `X-Msp360-Base-Url` — single global API host, no self-hosted/regional variant found.

**Vendor calls** (internal, inside `api_client.py` — not tool-level contracts, but documented here
since OQ1 covers their uncertainty):

```
POST https://api.mspbackups.com/api/Provider/Login
  body: {"UserName": "<from header>", "Password": "<from header>"}
  200 -> {"access_token": "...", "expires_in": <seconds>}
  401/403 -> credentials rejected

GET  /api/Computers/{hid}/Plans                      -> [ {Id, Name, Type, ...} ]
GET  /api/Computers/{hid}/Plans/{id}/info             -> {Status, LastStart, NextStart, ErrorMessage, ...}
GET  /api/Computers/{hid}/Plans/{id}/history?date.year=&date.month=&date.day=
                                                       -> [ {StartTime, Duration, Status, DataCopied, ...} ]
POST /api/Computers/{hid}/Plans/{id}/start  body: {"Mode": <mode?>}   -> {Status: "started", ...}
POST /api/Computers/{hid}/Plans/{id}/stop   body: {"Force": <force?>} -> {Status: "stopped", ...}
GET  /api/Monitoring[/{userId}]                       -> [ {PlanName, CompanyName, UserName, UserID,
                                                            ComputerName, Status, ErrorMessage,
                                                            LastStart, NextStart, PlanId, PlanType,
                                                            DataCopied, TotalData, ...} ]
```

**Tool contracts** (Agent-facing, returned as compact JSON strings per SOP §4.1):

```
msp360_list_plans(hid: str) -> {"plans": [{"id", "name", "type"}], "count": N}

msp360_get_plan_info(hid: str, plan_id: str)
  -> {"id", "status", "last_start", "next_start", "error_message"}

msp360_get_plan_history(hid: str, plan_id: str, year?: int, month?: int, day?: int)
  -> {"runs": [{"start_time", "duration_seconds", "status", "data_copied_bytes"}], "count", "has_more"}

msp360_start_plan(hid: str, plan_id: str, mode?: str) -> {"id", "status": "started"}
  annotations: destructiveHint=False, idempotentHint=False (starting twice may queue two runs —
  vendor behavior unconfirmed, documented as a caveat in the tool description rather than assumed)

msp360_stop_plan(hid: str, plan_id: str, force?: bool) -> {"id", "status": "stopped"}
  annotations: destructiveHint=True (cancels in-progress work), idempotentHint=True (stopping an
  already-stopped plan is a no-op per the vendor's own semantics, not an error — AC8 only covers
  genuinely invalid hid/plan_id, not "already stopped")

msp360_get_monitoring(user_id?: str, limit?: int = 50, offset?: int = 0)
  -> {"runs": [{"plan_id", "plan_name", "company_name", "computer_name", "user_id", "status",
               "last_start", "next_start", "error_message", "data_copied_bytes", "total_data_bytes"}],
      "count", "has_more"}
  limit default 50 / hard cap 200 (SOP §2.5); if the vendor call returns more than 200 records or the
  serialized result would exceed 20,000 characters, truncate to whichever bound is hit first and set
  has_more=true (SOP §2.5's "character cap wins" rule).
```

All list-shaped tools return trimmed, renamed fields (snake_case, only what §6 Test cases need) — not
the vendor's raw PascalCase payload — per SOP §2.5's field-trimming and token-economy rules.

**Error envelope** (SOP §4.2, used by all six tools):

| Vendor condition | `code` | `retryable` |
|---|---|---|
| `POST /api/Provider/Login` returns 401/403 | `unauthorized` | false |
| Any other call returns 401/403 after one retry-with-refreshed-token | `unauthorized` | false |
| Vendor returns 404 for an hid/plan_id combination | `not_found` | false |
| Vendor returns 400/422 (malformed hid/plan_id/date filter) | `invalid_argument` | false |
| Vendor returns 429 | `rate_limited` | true |
| Vendor returns 5xx, or connect/read timeout | `upstream_error` | true |
| Anything else unexpected | `upstream_error` | true |

Empty `plans`/`runs` lists are normal successful results (SOP §4.2 — "empty is not `not_found`"):
`not_found` is reserved for "this specific hid/plan_id doesn't exist."

**Backward compatibility**: N/A — brand-new tools, nothing to be compatible with. Tool names use the
`msp360_` prefix (SOP §2.8) so they cannot collide with the other MSP360 tools the sibling tickets
add, or with any other vendor's tools in the same Agent session.

### Key flow / sequence

```
Agent -> Gateway -> msp360-mcp: msp360_get_monitoring()
  msp360-mcp: have cached token for this credential fingerprint and not expired? use it.
              else: POST /api/Provider/Login with Header creds -> cache (token, expiry)
  msp360-mcp -> MSP360 API: GET /api/Monitoring  (Authorization: Bearer <token>)
  MSP360 API -> msp360-mcp: [ {CompanyName, ComputerName, PlanId, Status, ErrorMessage, ...}, ... ]
  msp360-mcp: trim/rename fields, cap at limit/20000 chars, set has_more
  msp360-mcp -> Agent: {"runs": [...], "count", "has_more"}

Agent (noticed PlanId=X on hid=Y has Status=error)
  -> msp360_get_plan_history(hid=Y, plan_id=X)        # recent run detail
  -> msp360_start_plan(hid=Y, plan_id=X)               # retry the backup
       msp360-mcp -> MSP360 API: POST /api/Computers/Y/Plans/X/start
       MSP360 API -> msp360-mcp: 200 {...}  (or 401 -> one re-login-and-retry -> still 401 -> unauthorized envelope)
       msp360-mcp -> Agent: {"id": "X", "status": "started"}
```

### Non-functional

- **Idempotency & concurrency**: `start_plan` is not idempotent by design (vendor semantics unknown —
  documented, not assumed safe); `stop_plan` is idempotent (stopping an already-stopped plan is a
  no-op). No local state is kept per call beyond the in-memory token cache (SOP §3.4's permitted
  exception — keyed by credential fingerprint, with expiry).
- **Performance**: `GET /api/Monitoring` with no filter could return one row per plan across the
  entire provider account — for an MSP with hundreds of endpoints this could be large. Hard cap of
  200 records / 20,000 serialized characters (whichever hits first) per SOP §2.5, `has_more` flag so
  the Agent knows to narrow by `user_id` rather than assume completeness. Outbound timeouts: 5s
  connect / 30s read (SOP §5); single call budget < 120s including retries.
- **Security**: Credentials only ever read from `X-Msp360-Username`/`X-Msp360-Password` headers, never
  env-var fallback (SOP §3.1); request-scoped via `contextvars.ContextVar` with `finally`-reset (SOP
  §3.3); token cache keyed by `(username, password)` fingerprint only, never shared across distinct
  credential pairs (SOP §3.4); no credential or vendor-response body ever logged (SOP §6, §11).
- **Multi-tenant isolation**: Every request carries its own tenant's MSP360 credentials in Headers;
  the Gateway, not this service, is what keeps tenant A's and tenant B's calls apart at the transport
  level — this service's only obligation (and the one AC10 pins down) is to never let one request's
  cached token leak into another credential fingerprint's lookup, which the `(username, password)`
  cache key already guarantees by construction.
- **Observability**: Structured log per call — tool name, hid/plan_id (not credentials), MSP360
  status code, latency, mapped error `code`. No vendor response bodies logged in full (may contain
  customer file paths/names from error messages — SOP §6, §11).
